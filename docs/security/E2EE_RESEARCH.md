## 1. 研究目的與範圍

本文件研究端對端加密（End-to-End Encryption，E2EE）在 ETHER 的適用性、公開成熟協定的概念、裝置金鑰生命週期、金鑰備份方案的比較、與一般聊天室的功能差異、伺服器不得明文儲存的邊界，以及上線前的風險清單。

研究範圍限於公開文獻與公開標準的概念介紹；具體的函式庫選型、協定參數、實作細節，須經使用者批准並經獨立審計後才可定案，本文件不代定。

## 2. E2EE 的基本定義

端對端加密是指：訊息內容只在傳送端與接收端裝置上加解密，伺服器無法取得明文。伺服器僅負責傳遞已加密的訊息密文與金鑰交換所需的公開資訊，不得儲存或讀取訊息明文。

與傳輸加密（TLS）與靜態加密的區別：

- 傳輸加密保護訊息在裝置與伺服器之間的傳輸過程，伺服器收到後可讀取明文。
- 靜態加密保護伺服器儲存的資料不被未授權的儲存層存取，但伺服器應用層在處理時仍可讀取明文。
- 端對端加密保護訊息內容不被伺服器讀取，即使伺服器被入侵或被要求提供資料，伺服器手上也只有密文。

ETHER 的 E2EE 啟用範圍與時程尚未決定（OQ-06）：是否全部對話預設啟用、群組對話是否同樣啟用、啟用前伺服器端搜尋與備份的替代方案為何，皆待使用者決定。本文件不代決定。

## 3. Signal Protocol 介紹

Signal Protocol 是公開審查過的成熟訊息加密協定，廣泛用於公開的即時通訊應用。本節僅介紹其公開概念，不複製實作程式碼，不宣稱 ETHER 已選定 Signal Protocol 的某一特定實作或函式庫；選型須經使用者批准。

### 3.1 協定組成（概念）

Signal Protocol 的概念組成，公開文獻一般描述為：

- **X3DH（Extended Triple Diffie-Hellman）**：非同步的金鑰協商協定，讓傳送端在接收端離線時，仍可利用接收端預先上傳至伺服器的公開金鑰材料，建立初始的共享秘密，開始加密會話。
- **Double Ratchet**：訊息金鑰輪替機制，結合 Diffie-Hellman Ratchet 與對稱金鑰 Ratchet，使每則訊息使用不同的訊息金鑰，並在每次往返中更新鏈金鑰。
- **身分金鑰（Identity Key）**：每裝置長期持有的金鑰對，用於識別裝置身份與簽署預共享金鑰；私鑰只存於裝置本機，公鑰可公開。
- **已簽署預共享金鑰（Signed Pre-Key）**：由身分金鑰簽署的中期金鑰，定期輪換；接收端預先上傳其公鑰部分至伺服器，供傳送端建立會話時使用。
- **一次性預共享金鑰（One-Time Pre-Key）**：一次性使用的預共享金鑰，接收端預先上傳一批至伺服器，每次建立會話消耗一個，用後即棄，增強前向保密。

### 3.2 Double Ratchet：訊息金鑰輪替

Double Ratchet 的核心概念是：訊息金鑰不斷向前推進，舊金鑰被丟棄，新金鑰由鏈金鑰衍生。每次訊息往返，雙方進行新的 Diffie-Hellman 交換，產生新的鏈金鑰，舊鏈金鑰不再使用。

效果：

- 每則訊息使用獨立的訊息金鑰，一則訊息的金鑰洩漏，不影響其他訊息的解密。
- 金鑰輪替是自動的，不需要使用者手動操作。
- 亂序與遺失的訊息，須以跳過金鑰（skipped keys）的機制處理，具體的保留數量與上限，須以實作與安全審查為準，本文件不預填數字。

### 3.3 X3DH：非同步會話建立

X3DH 解決的問題是：接收端離線時，傳送端如何開始加密會話。傳送端從伺服器取得接收端的身分公鑰、已簽署預共享金鑰公鑰與一個一次性預共享金鑰公鑰，結合自己的身分金鑰與臨時金鑰，進行多次 Diffie-Hellman 運算，衍生初始共享秘密。

伺服器在 X3DH 中的角色，僅為公開金鑰材料的分發者，不參與共享秘密的計算，不得取得共享秘密或訊息明文。

### 3.4 身分金鑰與一次性預共享金鑰的生命週期

| 金鑰 | 生命週期 | 儲存位置 |
|---|---|---|
| 身分金鑰對 | 長期，每裝置一對；裝置撤銷或重新安裝時更換 | 私鑰只存於裝置本機安全儲存；公鑰可上傳伺服器供他人驗證 |
| 已簽署預共享金鑰 | 中期，定期輪換；舊金鑰在一段時間後失效 | 私鑰只存於裝置本機；公鑰與簽名上傳伺服器 |
| 一次性預共享金鑰 | 一次性，每次會話建立消耗一個；用罄後裝置須補充上傳 | 私鑰只存於裝置本機；公鑰上傳伺服器，用後伺服器須刪除 |

裝置須監控一次性預共享金鑰的存量，存量不足時補充上傳；補充失敗時，新會話建立可能受影響，須有明確的錯誤處理，不得退回明文傳輸。

### 3.5 前向保密（Forward Secrecy）

前向保密是指：即使長期金鑰（例如身分金鑰）在未來洩漏，過去已傳送訊息的明文仍無法被解密。Double Ratchet 的訊息金鑰輪替與丟棄，是實現前向保密的關鍵：舊訊息金鑰已被丟棄，無法從當前金鑰反推。

前向保密的邊界：前向保密保護的是已刪除金鑰的過去訊息；若攻擊者在訊息傳送當下已取得訊息金鑰或裝置明文，前向保密並不保護該訊息。本文件不誇大前向保密的範圍。

### 3.6 後向保密／後洩漏安全（Post-Compromise Security）

後向保密（在公開文獻中亦稱 Post-Compromise Security，後洩漏安全）是指：即使某一時刻的金鑰狀態洩漏，經過後續的金鑰輪替（新的 Diffie-Hellman 交換），未來的訊息仍可恢復保密性。

Double Ratchet 的 Diffie-Hellman Ratchet 提供後向保密：每次往返的新交換，使鏈金鑰脫離洩漏的舊狀態。但後向保密的恢復，需要雙方繼續交換訊息以推進 Ratchet；若洩漏的裝置持續被控制，後向保密並不保證安全。裝置撤銷與金鑰更換，仍是必要的補救措施。

## 4. 裝置撤銷與新裝置驗證

### 4.1 裝置撤銷

裝置撤銷的觸發情形：使用者主動撤銷（遠端登出）、裝置遺失或被盜、裝置金鑰疑似洩漏、帳號安全事件。

撤銷的效果要求：

- 伺服器端：該裝置的身分公鑰與預共享金鑰須標記失效，不得再分發給傳送端；該裝置的 Session 與 Token 須撤銷；該裝置不得再同步新訊息。
- 裝置端：該裝置的本機金鑰與訊息明文快取須清除；清除須以裝置端確認為準，伺服器端不得宣稱已清除未連線裝置的本機資料。
- 其他裝置：其他裝置須得知該裝置已撤銷，不得再以舊金鑰向其加密新訊息；已加密給該裝置但尚未送達的訊息，處理方式待定案（是否重加密給其餘裝置、是否標記未送達，列為規格缺口）。

### 4.2 新裝置驗證

新裝置加入時，須經驗證，不得僅憑電話號碼或公開識別完成金鑰移轉。驗證方式的方向（待定案，列為規格缺口）：

- 既有裝置確認：既有裝置掃描或確認新裝置的安全碼，授權新裝置加入。
- 帳號驗證：經帳號密碼、MFA 或其他帳號驗證方式，授權新裝置建立新的身分金鑰。
- 安全金鑰驗證：使用者可比對雙方的安全碼（Safety Number 方向），確認對方身分金鑰未被替換；安全碼變更時，須有明確警告，不得靜默接受新金鑰。

新裝置的歷史訊息同步，在 E2EE 下受限：新裝置無法解密以舊裝置金鑰加密的歷史訊息，除非有金鑰備份或歷史訊息重加密機制；同步範圍與方式待定案，見第 5 節。

### 4.3 金鑰變更警告

對方身分金鑰變更時（例如對方重新安裝、更換裝置），本端須顯示明確警告，不得靜默接受新金鑰並繼續以舊會話傳送訊息。警告的呈現方式、使用者確認流程、確認前的訊息傳送限制，待定案。

## 5. 金鑰備份方案比較

金鑰備份的目的是：使用者更換裝置或重新安裝後，能恢復 E2EE 金鑰與歷史訊息的存取能力。備份方案的選擇，涉及安全性與可用性的權衡，尚未定案，本節只比較各方案的風險，不推薦、不代決定。

| 方案方向 | 說明 | 風險 |
|---|---|---|
| 裝置間直接移轉 | 舊裝置直接將金鑰傳輸至新裝置（例如本地連線、QR 掃描） | 須舊裝置在場且可操作；舊裝置遺失時無法恢復；傳輸過程須防竊聽與中間人，傳輸通道的安全性須審查 |
| 使用者口令加密備份 | 金鑰以使用者設定的口令加密後備份至伺服器或雲端儲存，恢復時以口令解密 | 口令強度決定備份安全性；口令遺失即無法恢復，不得提供口令找回或後門解密；伺服器端備份的存取控制與加密實作須審查；弱口令可能被暴力破解 |
| 既有裝置授權恢復 | 既有裝置授權新裝置，重新建立金鑰與會話，不恢復舊金鑰 | 須至少一台既有裝置在線且可操作；全部裝置遺失時無法恢復；歷史訊息無法以新金鑰解密，同步範圍受限 |
| 雲端託管金鑰備份（服務商持有） | 金鑰備份由服務商託管，恢復時經帳號驗證取回 | 服務商持有金鑰材料，E2EE 的信任邊界被削弱；服務商被入侵或被要求提供資料時，金鑰可能洩漏；須以法律意見與安全審查評估，不可輕率採用 |
| 不備份（重新建立金鑰） | 不提供金鑰備份，更換裝置即重新建立金鑰，歷史訊息無法在新裝置解密 | 可用性最低：換機即失去歷史訊息存取能力；但信任邊界最清晰，伺服器與備份皆不持有金鑰材料 |

共通風險：

- 任何備份方案，若備份檔包含私鑰或訊息明文，備份檔的存取控制、加密強度、保存期限，皆須與 E2EE 的信任邊界一致，不得以備份為名削弱 E2EE。
- 備份口令的 UX（設定、確認、遺失處理、換機移轉時的口令傳遞方式）待決定（OQ-05）。
- 備份方案未定案前，不得宣稱金鑰可安全備份或恢復，不得在介面中顯示未實作的備份功能。

## 6. 與一般聊天室的功能差異

E2EE 聊天室與一般聊天室，在功能上有明確差異，須在介面明確標示，不得讓使用者誤以為兩者功能相同：

| 功能 | 一般聊天室 | E2EE 聊天室（方向，待定案） |
|---|---|---|
| 伺服器端訊息搜尋 | 可經伺服器端全文搜尋（Meilisearch 自架方向） | 伺服器無法解密，搜尋須改為本機搜尋；本機搜尋的範圍與效能待定案 |
| 伺服器端備份與還原 | 可經伺服器端備份還原 | 備份須以加密備份或裝置間移轉為方向，伺服器端無法直接還原明文；備份方案待定案 |
| 多裝置同步 | 新裝置可同步歷史訊息 | 新裝置無法解密舊金鑰加密的歷史訊息，除非有金鑰備份或重加密機制；同步範圍受限 |
| 訊息內容審核 | 伺服器端可依檢舉進行內容審核（在合法合規範圍內） | 伺服器無法讀取明文，內容審核須以使用者端檢舉（附明文）為方向；審核流程待定案 |
| AI 功能 | 訊息明文可在授權與開關下送往 AI 服務（見 AI 資料處理規範） | E2EE 明文絕對不得自動送往任何 AI（含本地自架 AI 與外部 AI API）；本地 AI 亦須經授權與遮罩規範（見 AI_DATA_POLICY），不得以「本地即安全」為由繞過；AI 功能在 E2EE 聊天室的可用範圍待定案 |
| 垃圾訊息與惡意連結偵測 | 伺服器端可進行偵測 | 伺服器端無法讀取明文，偵測須以裝置端或使用者檢舉為方向；偵測能力受限 |
| 管理員存取 | 管理員可在最小權限範圍內存取必要的管理資料 | 管理員不得任意讀取 E2EE 訊息；E2EE 訊息的管理存取邊界待定案 |
| 通話內容 | 通話媒體以 WebRTC 加密傳輸，信令與媒體的 E2EE 範圍待定案 | 通話的 E2EE 範圍（媒體端對端加密）尚未定案，列為規格缺口 |

介面標示要求：E2EE 聊天室須有明確的端對端加密標示；一般聊天室不得顯示該標示；兩類聊天室的切換或升級流程（一般聊天室是否可升級為 E2EE、升級後歷史訊息的處理），尚未定案，列為規格缺口。

## 7. 伺服器不得明文儲存的邊界

在 E2EE 聊天室中，伺服器不得明文儲存或讀取下列內容：

- 訊息本文（文字、語音轉文字結果、檔案內容、圖片內容的明文）。
- 訊息金鑰、鏈金鑰、共享秘密、私鑰。
- 金鑰備份的明文或解密口令。
- 使用者以 E2EE 傳送的媒體檔案明文（媒體檔案的 E2EE 範圍待定案，見規格缺口）。

伺服器可以儲存的內容（在 E2EE 邊界內）：

- 訊息密文（已加密的訊息本體），僅供傳遞與離線投遞，不得嘗試解密。
- 公開金鑰材料：身分公鑰、已簽署預共享金鑰公鑰與簽名、一次性預共享金鑰公鑰。
- 詮釋資料：訊息的發送者、接收對象、時間戳記、對話識別碼、訊息狀態（送達、已讀），以及為路由與投遞所需的最小詮釋資料；詮釋資料的最小化範圍與保留期限，須以隱私權政策與保存政策為準，待定案。
- 密文的保留期限與刪除規則，須以保存政策為準，待定案（OQ-03 相關）。

邊界違規的後果：任何伺服器端明文儲存、明文日誌、明文備份、明文搜尋索引的行為，皆視為 E2EE 邊界違規，須立即通報並修復，不得以「僅供除錯」為由保留明文。

AI 邊界（鐵律）：E2EE 明文絕對不得自動送往任何 AI，含本地自架 AI（Ollama／vLLM／LocalAI）與外部 AI API。本地部署不等於可自由處理 E2EE 明文；任何 AI 處理 E2EE 內容，須經使用者明確授權、功能開關開啟與敏感資料遮罩規範（見 `docs/security/AI_DATA_POLICY.md`），預設一律禁止。E2EE 聊天室的 AI 功能預設關閉，開啟方式與範圍待定案。

| 編號 | 風險 | 說明 | 緩解方向（待定案） |
|---|---|---|---|
| R-E2EE-01 | 未經審計不得上線 | E2EE 實作未經獨立協定審計與實作審查，不得對外宣稱已端對端加密，不得上線 | E2EE Protocol Audit 列為 Phase 11 門檻；審計範圍、審計者、審計報告的公開範圍待定案 |
| R-E2EE-02 | 自發明加密演算法 | 自行設計加密演算法或修改成熟協定的核心流程，可能引入未被審查的弱點 | 優先採用公開審查過的成熟協定，不得自發明加密演算法；任何協定修改須經審查 |
| R-E2EE-03 | 金鑰管理失誤 | 私鑰上傳伺服器、私鑰明文儲存、私鑰備份不當，皆削弱 E2EE 信任邊界 | 私鑰只存於裝置本機安全儲存；備份方案須經安全審查；金鑰管理程式碼須經審查 |
| R-E2EE-04 | 裝置撤銷不即時 | 撤銷後舊裝置仍可解密新訊息，或伺服器仍分發已撤銷裝置的公鑰 | 撤銷即時生效於伺服器端；撤銷狀態的同步與驗證須經測試 |
| R-E2EE-05 | 中間人攻擊 | 攻擊者替換身分公鑰，冒充對方建立會話 | 安全金鑰驗證（Safety Number 方向）與金鑰變更警告；驗證流程須經可用性與安全審查 |
| R-E2EE-06 | 群組 E2EE 複雜度 | 群組成員變更（加入／離開／移除）時的金鑰分發與前向保密，較一對一複雜，成員離開後仍可解密舊訊息的風險須處理 | 群組 E2EE 的金鑰分發機制（例如 Sender Keys 方向）須經研究與審計；群組啟用範圍待決定（OQ-06） |
| R-E2EE-07 | 備份削弱 E2EE | 金鑰備份或訊息備份的實作不當，使伺服器或備份服務可取得明文 | 備份方案須經安全審查；備份的加密與存取控制須與 E2EE 邊界一致 |
| R-E2EE-08 | 詮釋資料洩漏 | 伺服器可見的詮釋資料（誰與誰通訊、何時、多頻繁）可能洩漏隱私，即使內容加密 | 詮釋資料最小化、保留期限、存取控制，須以隱私權政策為準；Sealed Sender 方向的研究待定案（列為規格缺口） |
| R-E2EE-09 | 函式庫供應鏈風險 | 加密函式庫的版本、來源、完整性驗證失誤，可能引入惡意或脆弱的程式碼 | 函式庫選型須經批准；版本固定、完整性驗證、Dependency Scan 列為 Phase 11 門檻 |
| R-E2EE-10 | 使用者誤解 | 使用者誤以為一般聊天室亦為 E2EE，或誤以為 E2EE 保護詮釋資料與裝置安全 | 介面標示須明確區分兩類聊天室；使用者教育內容須經審查，不得誇大保護範圍 |
| R-E2EE-11 | 媒體 E2EE 範圍不明 | 圖片、影片、檔案、語音訊息的 E2EE 範圍尚未定案，媒體可能以一般加密傳輸而非 E2EE | 媒體 E2EE 的範圍與實作，須在 E2EE 實作前定案，不得以文字訊息的 E2EE 宣稱涵蓋媒體 |
| R-E2EE-12 | 檢舉與審核受限 | E2EE 下伺服器無法讀取明文，檢舉與內容審核的能力受限，可能影響兒少保護與垃圾訊息防制 | 檢舉流程須以使用者端附明文為方向，審核流程與人力待定案（OQ-07） |
| R-E2EE-13 | 法規與跨境傳輸 | E2EE 訊息的跨境傳輸、資料保存、執法請求的處理，須以法律意見為準 | 跨境傳輸目的地與法律意見待定案；本文件不提供法律意見 |
| R-E2EE-14 | E2EE 明文送往 AI | 將 E2EE 明文自動送往任何 AI（含本地自架 AI），破壞端對端信任邊界；「本地即安全」的假設不可作為繞過授權與遮罩的理由 | 鐵律禁止預設傳輸；本地 AI 亦須授權、開關與遮罩；見 AI_DATA_POLICY |

## 9. 研究結論與待決定事項

1. Signal Protocol 的公開概念（Double Ratchet、X3DH、身分金鑰、一次性預共享金鑰、前向保密、後向保密）適用於 ETHER 的 E2EE 研究方向，但具體選型、函式庫、參數，須經使用者批准，本文件不宣稱已選定。
2. E2EE 的啟用範圍與時程（OQ-06）、金鑰備份方案、群組 E2EE 機制、媒體 E2EE 範圍、新裝置驗證方式，皆尚未定案，須由使用者決定。
3. E2EE Protocol Audit 列為 Phase 11 門檻，未經審計不得上線，不得對外宣稱已端對端加密。
4. E2EE 與一般聊天室的功能差異、伺服器不得明文儲存的邊界，須在實作前定案並寫入 API 與 ERD 文件。
