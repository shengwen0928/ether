# ETHER AI 資料處理規範（AI_DATA_POLICY）

> 依據：`SPEC-SOURCE.md` 手冊 K（Phase 09 ETHER AI）、§17（隱私與安全）、架構調整指令（2026-11-25 00:33）：AI 採 Ollama＋vLLM＋LocalAI 優先＋外部 AI API Adapter 可選擴充；`MASTER_SPEC.md` 第 1 節（訊息翻譯遠期）、第 7 節（官方帳號自動回覆）為功能深度補充。
>
> 本文件為 Phase 00 規範文件，不構成完成宣告、不是模型選型決定、不是效能承諾。任何 AI 功能在以真實模型供應商或可驗證的自架服務驗收之前，一律視為未完成。成本一律寫「待查證」。未決事項只列問題，不代決定。

## 1. 總則與鐵律

### 1.1 目的

本文件規範 ETHER 全部 AI 功能的資料邊界：哪些資料可以送往 AI、須經何種授權、如何遮罩、如何防護提示注入、工具權限如何限制、用量如何計量與保留。適用於本地自架 AI 與外部 AI API，兩者適用同一規範，本地部署不等於較寬鬆的邊界。

### 1.2 鐵律（不得違反）

1. **E2EE 明文絕對不得自動送往任何 AI。** 含本地自架 AI（Ollama／vLLM／LocalAI）與外部 AI API。E2EE 聊天室的 AI 功能預設關閉；任何例外須經使用者明確授權、功能開關開啟與敏感資料遮罩三者同時成立，且須留存授權紀錄。預設一律禁止，不得以「本地即安全」「模型在本機」為由繞過。
2. **不得自發明加密演算法；不得將 AI 用於削弱 E2EE。** AI 不得用於推測、還原或繞過加密金鑰，不得存取私鑰。
3. **供應商不得寫死在商業邏輯。** 商業邏輯只依賴 AI Provider Adapter 介面，不得直接依賴特定供應商 SDK、特定模型名稱或特定供應商的請求格式。
4. **無模型、無 Key 時只做介面並標記未完成。** 不得以假回應、固定範本冒充 AI 結果；AI 回應須標示來源模型與是否為真實模型輸出（標示方式待定案）。
5. **不得編造額度、數字或效能指標。** Token Budget、Rate Limit、資源需求的具體數字，凡未經實測者一律寫「待定／待查證／待實測」，不得作為承諾。

### 1.3 適用範圍

本文件適用於手冊 K 全部 AI 功能（見第 7 節逐項資料邊界）：AI 對話、訊息 AI（摘要、翻譯、智慧回覆、潤飾、語氣、語音轉文字、文件摘要、圖片理解）、知識 AI（個人知識庫、文件索引、向量搜尋、RAG、語意搜尋）、商業 AI（官方 AI 客服、FAQ、Bot、分類、摘要、回覆建議）。

## 2. AI 架構：Ollama＋vLLM＋LocalAI 優先＋外部 AI API Adapter 可選擴充

### 2.1 架構原則

```
使用者／對話／Bot／管理後台
        │  （授權、開關、遮罩、預算檢查皆在此層之前完成）
        ▼
AI Provider Adapter（單一介面，商業邏輯只依賴此層）
        ├─ 本地優先：Ollama（模型管理與推理）／vLLM（高吞吐推理服務）／LocalAI（相容介面閘道，方向）
        ├─ 向量檢索：pgvector（已定案，見 ADR-017）
        └─ 可選擴充：外部 AI API（經 Adapter 封裝，須有 Key 與使用者決定才啟用）
        ▼
模型執行環境（自架伺服器，資源管理見第 8 節）
```

- **本地優先**：預設以自架模型提供 AI 功能，資料不出自架邊界（在授權與遮罩成立的前提下）。本地優先不等於 E2EE 明文可自由送往本地 AI（見鐵律）。
- **外部可選擴充**：外部 AI API 僅為可選擴充，須經使用者決定、Key 設定、資料邊界確認後才啟用；未啟用時，外部路徑不得被呼叫，不得以靜默降級送往外部。
- **三者分工（方向，待部署文件定案）**：Ollama 偏向模型下載、管理與輕量推理；vLLM 偏向高併發、高吞吐的推理服務；LocalAI 偏向提供相容介面的本地推理閘道。三者是否同時部署、如何分流，待部署與效能實測定案，本文件不預設三者皆須同時運作。
- **部署驗證**：Docker Compose 啟動／連線／AI 切換皆為「待 CI 或有 Docker 的環境驗證」，此 VM 無 docker，不得寫已驗證。

### 2.2 Provider Adapter 原則

1. 商業邏輯（聊天、摘要、翻譯、RAG、客服）只呼叫 Adapter 介面（例如：對話補全、串流補全、嵌入、語音轉文字、圖片理解，介面名待 API 文件定案），不得直接 import 供應商 SDK，不得在商業邏輯中寫入供應商的端點、模型名稱或請求格式。
2. Adapter 負責：請求格式轉換、認證（Key 以 OpenBao 管理，不得寫入原始碼）、重試與退避、逾時、錯誤轉譯、Token 計量回傳、串流事件轉換。
3. 模型切換：模型選擇為設定項，可在 Adapter 層切換本地模型與外部模型，不得要求改商業邏輯程式碼；切換時須記錄模型識別碼於使用紀錄（見第 9 節），不得以切換為由改變資料邊界。
4. 供應商不得寫死：模型清單、預設模型、備援順序，皆為設定項，不得硬編碼於商業邏輯；設定變更須留存紀錄。
5. 測試：Adapter 須有契約測試，以可驗證的自架服務或供應商測試端點驗收；無 Key、無模型時，Adapter 須回傳明確的「未設定」錯誤，不得回傳假內容。

### 2.3 可切換模型

- 使用者（或管理員，依功能而定）可在已授權的模型清單內切換模型；清單內容、預設模型、切換權限，待定案。
- 切換模型不得改變資料邊界：切換至外部模型時，外部資料邊界（見第 7 節）重新適用，不得沿用本地模型的邊界假設。
- 模型切換須即時生效於新請求，已進行中的串流請求不受影響；切換紀錄留存於使用紀錄。

### 2.4 Streaming（串流輸出）

- AI 對話支援 Streaming：模型輸出以串流事件逐步回傳，前端逐步顯示，不得要求等待完整回應才顯示。
- 串流中斷（斷網、逾時、模型錯誤）時，已輸出的部分須明確標示為「未完成」，不得假裝完整；重試須以新請求重新產生，不得以舊片段拼湊冒充完整回應。
- 串流內容的遮罩與安全檢查，須在完整回應層級與串流片段層級同時考慮：不得以串流為由跳過遮罩或內容安全檢查；檢查方式待定案。

### 2.5 Tool Calling（工具呼叫）

- 模型可經 Tool Calling 呼叫 ETHER 內部工具（例如搜尋、查詢對話摘要、查詢知識庫），工具清單與權限見第 6 節。
- Tool Calling 的工具呼叫，須經 Adapter 層驗證工具名稱與參數，不得由模型直接呼叫任意後端 API；模型輸出的工具參數須經後端驗證，不得直接信任。
- 工具呼叫的結果回傳給模型前，須經資料邊界檢查：不得將 E2EE 明文、使用者私密資料、其他使用者的資料，經工具結果洩漏給模型（見第 6、7 節）。

### 2.6 上下文管理

- 對話上下文（歷史訊息、對話摘要、知識庫片段）納入 AI 請求前，須經授權、開關與遮罩檢查；上下文範圍（最近訊息數、時間範圍、是否含媒體描述）為設定項，待定案，不得以無上限的上下文送往 AI。
- 上下文須遵守對話存取權限：不得將使用者無權存取的對話、已封鎖範圍的內容、已刪除的內容納入上下文。
- 上下文超出模型限制時，須以截斷、摘要或拒絕的方式處理，不得靜默丟棄關鍵授權資訊；處理方式須可說明。
- 上下文不得含 E2EE 明文（鐵律）；E2EE 對話的上下文納入方式，待定案，預設為不納入。

### 2.7 Token 統計

- 每次 AI 請求，Adapter 須回傳 Token 統計（輸入 Token、輸出 Token，計量方式以模型與供應商的計量為準，待定案）；統計須寫入使用紀錄（見第 9 節），不得僅以前端估算代替。
- Token 統計用於預算管理（見第 8 節）與成本估算；統計數字不得對外宣稱為精確計費數據，除非供應商的計費方式已查證。
- 本地模型的 Token 計量，以本地推理服務的回傳為準；計量不一致時，以服務端回傳為準，不得以客戶端估算覆寫。

### 2.8 資源管理（AI 服務層）

- AI 請求須經佇列與併發控制：併發上限、佇列長度、等待逾時，皆為設定項，待實測定案；超過上限時明確拒絕或排隊，不得無限制併發拖垮推理服務。
- 模型載入與卸載：模型按需載入，閒置模型可卸載以釋放資源；載入狀態須可觀測（Prometheus＋Grafana＋Loki＋OpenTelemetry 監控覆蓋 AI，見 COST_OPTIMIZATION）。
- 降級策略：本地模型不可用時，不得自動降級至外部 AI API（須經授權與使用者決定）；不得以降級為由改變資料邊界。
- 資源需求評估見第 10 節。

## 3. 授權與開關

| 層級 | 授權內容 |
|---|---|
| 使用者級開關 | 使用者可開啟／關閉 AI 功能（全部或逐項，粒度待定案）；關閉後，AI 不得處理該使用者的任何內容，不得以背景任務為由繼續處理 |
| 對話級授權 | 群組與一對一對話的 AI 功能（例如群組摘要），須經對話成員的授權規則（規則待定案）；E2EE 對話預設關閉，見鐵律 |
| 功能級授權 | 每項 AI 功能（摘要、翻譯、RAG、客服）有獨立開關；開啟某項不代表開啟其他項 |
| 官方帳號／Bot 級授權 | 官方帳號的 AI 客服，須經官方帳號擁有者的授權；Bot 的 AI 功能，須經 Bot 申請時的權限範圍，不得超出 |
| 管理員級授權 | 管理員可設定模型清單、預算、Rate Limit 與全域開關；管理員不得以管理權限繞過使用者的 AI 開關，不得強制開啟使用者已關閉的 AI 功能 |

- 授權變更即時生效於新請求，已進行中的請求不受影響；授權撤銷後，不得再以舊授權處理新內容。
- 授權紀錄須留存（誰、何時、開啟／關閉何項功能），保留期限待定（見第 9 節）。
- 未成年人帳號的 AI 功能授權，年齡門檻與法定代理人同意方式待法律意見確認（OQ-13）；門檻未確認前，不得以自行推測的年齡判定。

## 4. 敏感資料遮罩

### 4.1 遮罩原則

- 送往 AI 的內容，須先經遮罩處理：移除或替換敏感資料，不得以原文送往 AI（本地 AI 亦同，鐵律的授權與遮罩要求同時適用）。
- 遮罩為可設定的規則集，規則變更須留存紀錄；遮罩失敗（無法識別敏感資料）時，須以拒絕或更嚴格的遮罩處理，不得以原文送往 AI。

### 4.2 遮罩類別（方向，具體規則待定案）

| 類別 | 處理方向 |
|---|---|
| 密碼、Token、API Key、憑證 | 一律遮罩，不得送往 AI；日誌與使用紀錄亦不得含明文 |
| 電話號碼、Email、地址、身分證件號碼 | 依功能必要性遮罩；非必要時一律遮罩；必要時須經授權並以最小範圍傳送 |
| 金融資訊（卡號、帳號） | 一律遮罩，不得送往 AI |
| 健康、位置精確資訊 | 依功能必要性遮罩；非必要時一律遮罩 |
| E2EE 明文 | 絕對不得自動送往任何 AI（鐵律）；遮罩不得作為繞過鐵律的理由——遮罩後的 E2EE 內容是否可送往 AI，須經授權與定案，預設為不可 |
| 其他使用者的私密資料 | 不得經上下文、工具結果或知識庫片段，洩漏給無權存取的使用者或模型 |

### 4.3 遮罩與功能完整性的權衡

- 遮罩可能降低 AI 回應品質；品質下降不得以放寬遮罩為代價，須以功能設計（例如僅送摘要、僅送結構化資料）解決。
- 遮罩規則的測試：須以測試案例驗證敏感資料不洩漏，測試案例不得含真實個人資料。

## 5. Prompt Injection 防護

### 5.1 威脅模型

Prompt Injection 是指：攻擊者將指令藏於訊息內容、檔案內容、網頁預覽、Bot 回覆、知識庫文件等非指令來源中，誘使模型執行非預期的指令（例如洩漏資料、呼叫工具、繞過授權）。

### 5.2 防護原則

1. **指令與資料分離**：系統指令、開發者指令、使用者指令、工具結果、訊息內容，須以不同角色與標記區分；模型不得將訊息內容、檔案內容、工具結果視為指令。
2. **不信任內容**：訊息內容、檔案內容、網頁內容、Bot 訊息、知識庫文件，皆視為不信任資料，不得直接作為指令執行；其中含有的指令式文字，須視為資料，不得執行。
3. **工具呼叫驗證**：模型提出的工具呼叫，須經後端驗證工具名稱、參數範圍與授權；具後果的操作（發訊、修改設定、存取私密資料）須經使用者確認，不得由模型自行決定。
4. **輸出驗證**：模型輸出在顯示或執行前，須經格式與內容驗證；輸出中含有的連結、指令、敏感資料，須經檢查，不得直接渲染為可執行的操作。
5. **最小權限**：模型可呼叫的工具，僅限白名單內的唯讀或低風險工具（見第 6 節）；模型不得呼叫管理員工具、不得修改權限、不得存取其他使用者的資料。
6. **日誌與通報**：疑似 Prompt Injection 的嘗試，須留存紀錄（不含敏感明文）並通報，具體通報流程待定案。

### 5.3 不得仰賴的防護

- 不得以「模型很聰明，會自行分辨」作為防護依據；防護須以後端驗證與權限檢查為準。
- 不得以關鍵字黑名單作為唯一防護；黑名單可作為輔助，不得作為唯一依據。

## 6. Tool 權限

| 原則 | 說明 |
|---|---|
| 白名單 | 模型僅可呼叫白名單內的工具；白名單由管理員設定，變更留存紀錄；未列入白名單的工具，一律拒絕 |
| 最小權限 | 工具僅能存取授權範圍內的資料；工具不得存取 E2EE 明文、其他使用者的私密資料、管理員資料 |
| 參數驗證 | 工具參數須經後端驗證範圍與型別；參數含敏感資料時，須經遮罩檢查 |
| 具後果操作須確認 | 發送訊息、修改設定、建立／刪除資料、呼叫外部服務等具後果的操作，須經使用者明確確認，不得由模型自行執行 |
| 工具結果邊界 | 工具結果回傳給模型前，須經資料邊界檢查；結果不得含 E2EE 明文、私密資料、其他使用者的資料 |
| 工具呼叫紀錄 | 每次工具呼叫須留存紀錄（工具名、參數摘要、結果摘要、授權狀態），不得含敏感明文 |

## 7. 手冊 K 全部 AI 功能的逐項資料邊界

| 功能 | 資料邊界 |
|---|---|
| AI 對話（Streaming、模型切換、上下文、歷史、用量、設定、Tool Calling） | 僅在使用者開啟 AI 對話開關後，可將使用者輸入與授權範圍內的上下文送往 Adapter；E2EE 對話預設關閉；歷史上下文範圍待定；Tool Calling 見第 6 節；用量與設定見第 8、9 節 |
| 訊息摘要（單則與群組摘要） | 僅在授權與開關開啟後，可將授權範圍內的訊息摘要輸入送往 AI；E2EE 訊息不得自動送往 AI；摘要結果僅顯示於請求者本機，不得回寫伺服器或分享給未授權者 |
| 訊息翻譯 | 翻譯結果只顯示於本機，不得覆寫原文、不得回寫伺服器；翻譯供應商（本地或外部）待決定（OQ-09／NQ-04）；E2EE 訊息的翻譯邊界待定案，預設關閉；翻譯內容是否傳送至第三方服務，須經授權並揭露 |
| 智慧回覆、潤飾、語氣 | 僅在使用者主動觸發後，可將該則訊息的內容（經遮罩）送往 AI；建議結果僅供使用者確認後傳送，不得自動傳送 |
| 語音轉文字 | 語音檔案的轉文字，僅在使用者主動觸發後進行；轉文字結果的保存與 AI 傳送邊界待定案；E2EE 語音訊息的轉文字邊界待定案，預設關閉 |
| 文件摘要 | 僅在使用者主動觸發後，可將使用者有權存取的文件（經遮罩）送往 AI；文件內容不得含 E2EE 明文（鐵律）；摘要結果僅顯示於請求者 |
| 圖片理解 | 僅在使用者主動觸發後，可將使用者有權存取的圖片（經遮罩與縮放，具體方式待定案）送往 AI；圖片內容不得含 E2EE 明文；圖片理解不得用於識別使用者身份以外的用途 |
| 知識 AI：個人知識庫、文件索引、向量搜尋、RAG、語意搜尋 | 知識庫文件須經使用者授權上傳與索引；索引與向量資料須有權限隔離：使用者僅能檢索自己有權存取的文件；刪除文件時，向量索引須同步刪除；RAG 檢索結果納入 AI 請求前，須經權限與遮罩檢查；向量資料庫用 pgvector（已定案，見 ADR-017） |
| 商業 AI：官方 AI 客服、FAQ、Bot、分類、摘要、回覆建議 | 僅在官方帳號擁有者授權後，可將客服對話（經遮罩）送往 AI；FAQ 與知識內容須經擁有者確認；Bot 的 AI 功能不得超出 Bot 申請的權限範圍；客服對話的 E2EE 邊界（如適用）待定案，預設關閉 |
| 官方帳號自動回覆（關鍵字、歡迎／離線訊息） | 自動回覆規則為確定性規則，不須 AI 即可運作；AI 客服與確定性自動回覆的邊界須明確，不得以 AI 回覆冒充確定性規則的回覆 |

## 8. Token Budget／Rate Limit

- **Token Budget**：每使用者、每對話、每官方帳號的 Token 預算，為設定項，具體數字待定，不得編造；預算耗盡時明確拒絕或提示，不得靜默降級或以假內容冒充。
- **Rate Limit**：每使用者、每 IP、每 Bot 的 AI 請求頻率限制，由後端強制，不得僅靠前端節流；限制值待定，須以實測與成本評估定案。
- **成本控制**：本地模型的成本以伺服器資源成本為主（見第 10 節）；外部 AI API 的成本以供應商計價為準，待查證；預算與成本的監控，納入 Prometheus＋Grafana＋Loki 監控覆蓋範圍。
- **預算與 Rate Limit 的變更**，須留存紀錄，並通知受影響的使用者（在適當範圍內）。

## 9. 使用紀錄與保留策略

### 9.1 記錄內容（僅詮釋資料，不得含明文）

| 欄位方向 | 說明 |
|---|---|
| 請求識別碼、時間戳記 | 用於追蹤與稽核 |
| 使用者識別碼、對話／官方帳號識別碼 | 用於授權與預算歸屬 |
| 功能名稱、模型識別碼、Adapter 路徑（本地／外部） | 用於模型切換與成本歸屬 |
| Token 統計（輸入／輸出） | 用於預算與成本 |
| 授權狀態（開關、授權紀錄識別碼） | 用於證明授權成立 |
| 工具呼叫紀錄（工具名、授權狀態） | 用於 Tool 權限稽核 |
| 結果狀態（成功／失敗／拒絕原因） | 用於除錯與監控 |

### 9.2 不得記錄的內容

- 訊息明文、E2EE 明文、遮罩前的敏感資料、密碼、Token、API Key 明文，一律不得寫入使用紀錄、日誌或監控資料。
- 模型輸出的完整明文，是否記錄，待定案；預設為不記錄完整明文，僅記錄摘要或狀態。

### 9.3 保留策略

- 使用紀錄的保留期限待定（與 OQ-03 保存政策協調）；期限屆滿後刪除或去識別化，刪除執行須留存紀錄（僅類別與筆數，不得含內容）。
- 使用者可申請查詢自己的 AI 使用紀錄（在適當範圍內）；查詢流程待定案。

## 10. 資源需求評估：CPU／RAM／GPU／VRAM（分模型規模等級）

> 警告：本節的區間一律標「待查證／待實測」，不得作為採購、部署或效能承諾。實際需求取決於模型參數量、量化方式、上下文長度、併發數、推理框架（Ollama／vLLM／LocalAI）與硬體型號，須以實測為準。不得假設一般伺服器跑得動所有模型。

| 等級（方向） | 模型規模方向 | 資源需求區間（待查證／待實測） | 備註 |
|---|---|---|---|
| 小型 | 輕量模型，適用於摘要、分類、智慧回覆等低複雜度任務 | CPU：多核心，具體核心數待查證；RAM：區間待查證（方向：數 GB 至十數 GB）；GPU／VRAM：可僅用 CPU 運作，GPU 為可選加速，VRAM 區間待查證 | 須實測併發與延遲後定案；不得假設單機可同時支撐大量併發 |
| 中型 | 中等規模模型，適用於一般對話、翻譯、RAG 等任務 | CPU：多核心，具體核心數待查證；RAM：區間待查證（方向：十數 GB 至數十 GB）；GPU／VRAM：建議 GPU 加速，VRAM 區間待查證（方向：十數 GB 級，依量化與上下文而定） | 須實測上下文長度與併發的影響；GPU 記憶體不足時不得以降低精度冒充原模型效果 |
| 大型 | 大規模模型，適用於高複雜度對話、文件摘要、圖片理解等任務 | CPU：多核心，具體核心數待查證；RAM：區間待查證（方向：數十 GB 至百 GB 級）；GPU／VRAM：須 GPU，VRAM 區間待查證（方向：數十 GB 級以上，依模型與量化而定），可能須多卡 | 不得假設一般伺服器跑得動；須以實測與成本評估決定是否採用大型模型，或改用外部 AI API（須經授權與資料邊界確認） |
| 外部 AI API（可選擴充） | 供應商託管模型 | 本地 CPU／RAM／GPU 需求不適用；成本以供應商計價為準，待查證；頻寬與延遲取決於網路，待實測 | 資料邊界見第 7 節；外部路徑須經授權才啟用 |

- 資源評估的待辦：Phase 09 開始前，須以候選模型、候選量化方式、目標上下文長度與目標併發數，進行實測並記錄 CPU／RAM／GPU／VRAM 的實測數據，寫入部署文件；實測前不得對外宣稱某模型可在某硬體上運作。
- 資源不足時的處理：明確拒絕或排隊，不得以靜默降級至較小模型冒充原模型，不得以降低上下文、截斷內容冒充完整處理。

## 11. 無 Key／無模型時只做介面並標記未完成

- 本地模型未部署、外部 Key 未設定、Adapter 未設定時，AI 功能只做介面（開關、設定頁、模型清單的佔位狀態），並明確標記「未完成／未設定」，不得顯示假的 AI 回應、假的摘要或假的翻譯。
- 無 Key 時的驗收：介面可開啟、設定可儲存、請求回傳明確的「未設定」錯誤、不得產生假內容、不得呼叫未設定的外部端點。
- 有 Key 但未經使用者決定啟用外部路徑時，外部路徑不得被呼叫；啟用決定須留存紀錄。
