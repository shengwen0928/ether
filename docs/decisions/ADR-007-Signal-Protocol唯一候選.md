狀態：草案／待批准

# ADR-007：Signal Protocol 為 E2EE 唯一候選（不得自研演算法，待審計）

- **狀態**：已決定（草案／待批准）；審計待進行
- **日期**：2026-11-25（Phase 00）
- **依據**：SPEC-SOURCE.md §17、手冊 A（不得自發明密碼學協定）

## 問題

E2EE 應採何種協定？是否可以自研加密演算法？

## 選項

| 選項 | 說明 |
|---|---|
| A. Signal Protocol（公開審查過的成熟協定） | SPEC-SOURCE.md §17 明文優先採用；每裝置獨立金鑰、身分金鑰、一次性金鑰、訊息金鑰輪替、前向保密、裝置撤銷、金鑰備份、新裝置驗證、安全金鑰驗證皆有現成協定語義 |
| B. 自研加密演算法／協定 | 禁止：SPEC-SOURCE.md §17「不得自發明加密演算法」、手冊 A「不得自發明密碼學協定」 |
| C. 傳輸層 TLS 即視為 E2EE | 錯誤：TLS 只保護傳輸，伺服器仍可讀明文；E2EE 要求伺服器不可讀明文（見 `SECURITY_ARCHITECTURE.md` §7） |

## 決定

選 A：Signal Protocol 為 E2EE 唯一候選。任何 E2EE 實作皆須以 Signal Protocol 的公開協定語義為基礎，不得自研演算法、不得自創金鑰交換或 Ratchet 變體；實作完成後須經協定審計（審計方與範圍待定），審計未通過不得對外宣稱 E2EE 已驗證。

## 理由

1. 密碼學協定的正確性無法以「編譯通過」或「訊息能通」證明，必須依賴公開審查與審計；自研協定是已知的高風險做法，規格已明文禁止。
2. E2EE 邊界（伺服器不可讀明文）是架構紅線，協定選擇錯誤即邊界失效，無法事後修補。
3. 群組 E2EE、E2EE 與一般聊天室的功能差異、金鑰備份方式，皆待 E2EE 研究文件定案，不得在本 ADR 預設。

## 後果

- E2EE 研究文件為 Phase 11 前置阻塞文件之一；未定案前，訊息流程文件須以「E2EE 路徑待回填」標註缺口（見 `DATA_FLOW.md` §11）。
- 本決定不涉及花錢或綁卡；審計若需付費，須由使用者決定（不得代決定）。
