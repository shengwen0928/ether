# ADR-012：可觀測性自架（Prometheus＋Grafana＋Loki＋OpenTelemetry＋GlitchTip）

- **狀態**：已決定（草案／待批准）
- **日期**：2026-11-25 00:33（使用者架構調整指令）
- **依據**：SPEC-SOURCE.md 頂部「架構調整」一節、§19（系統管理）、手冊 C（Health Check、Logging、OpenTelemetry）

## 問題

可觀測性應如何改採自架方案，同時覆蓋 API、WebSocket、資料庫、Worker、Media、AI 全部鏈路？

## 選項

| 選項 | 說明 |
|---|---|
| A. Prometheus＋Grafana＋Loki＋OpenTelemetry＋GlitchTip 自架 | 符合架構調整指令；指標、日誌、追蹤、錯誤追蹤四者分工明確 |
| B. 託管監控服務 | 已被使用者指令取代，不得繼續 |
| C. 只留日誌，不做指標／追蹤 | 不可行：§19 系統管理要求 API／WebSocket／資料庫／佇列／儲存監控與警報；無指標即無擴充決策依據（見 `SCALABILITY.md` §1） |

## 決定

選 A：監控採 Prometheus＋Grafana＋Loki＋OpenTelemetry＋GlitchTip（全部自架）。覆蓋範圍：API、WebSocket、資料庫、Worker、Media、AI（另含 LiveKit CE 與 NATS，見下）。

## 分工與覆蓋

| 元件 | 職責 | 覆蓋對象 |
|---|---|---|
| OpenTelemetry | Trace／Metrics／Logs 的統一接入與關聯（Trace ID 貫穿全鏈路） | API、Gateway、Worker、LiveKit CE、Media 處理、AI Adapter |
| Prometheus | 指標抓取與儲存 | API 延遲、WS 連線數與重連率、訊息投遞延遲與重試率、NATS 佇列積壓與死信數、Worker 延遲、媒體上傳成功率、通話建立成功率與 TURN 中繼率、推播送達率、資料庫連線池與慢查詢、AI 延遲與 Token 統計、儲存用量 |
| Grafana | 儀表板與告警呈現 | 全部指標；管理後台的系統健康呈現經 Grafana 或管理後台介面擇一，不得兩套數字不一致（呈現方式待定） |
| Loki | 日誌聚合（結構化日誌，Trace ID 關聯） | 全部服務；日誌去敏規則見 `SECURITY_ARCHITECTURE.md` §8（不得含 Token／金鑰／E2EE 明文） |
| GlitchTip | 錯誤追蹤（應用錯誤與例外，自架） | API、Gateway、Worker、Web／Admin 前端錯誤（前端接入方式待定）；不得含敏感資料 |

## 理由

1. 架構調整指令明定此組合與覆蓋範圍；四者分工是業界常見的自架可觀測性組合，無單一元件可獨自覆蓋指標＋日誌＋追蹤＋錯誤。
2. 擴充決策（`SCALABILITY.md` §1「先量測，後擴充」）以此為唯一證據來源；無可觀測性即無擴充依據。
3. 告警規則與管道待定（見 MASTER_SPEC.md 未決問題 OQ-12 概念）：Grafana 告警的通知對象與管道須由使用者決定，不得在本 ADR 預設。

## 後果

- 保留策略（Trace 取樣率、指標／日誌保留期限、磁碟容量）待查證（自架主機磁碟），不得編造；保留策略須與法規保留要求對齊。
- 全部元件以容器部署於同一 Docker Compose＋Coolify 架構內；驗證為「待 CI 或有 Docker 的環境驗證」。
- 本決定不涉及花錢或綁卡；自架主機的磁碟與運算成本屬 ADR-009 的伺服器成本，待查證。
