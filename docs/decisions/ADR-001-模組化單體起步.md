# ADR-001：模組化單體起步（vs 微服務拆分）

- **狀態**：已決定（草案／待批准）
- **日期**：2026-11-25（Phase 00）
- **依據**：SPEC-SOURCE.md（22 模組、§26 目錄規範、手冊 C Phase 01）

## 問題

ETHER 後端起步應採模組化單體，還是直接拆為微服務？22 個模組（Authentication、User、Profile、Friend、Contact、Chat、Message、Group、Community、Media、Sticker、Call、Notification、Search、Official Account、Bot、Timeline、Payment Integration、Moderation、Administration、Analytics、Device Management）的邊界已定，但部署形態未定。

## 選項

| 選項 | 優點 | 缺點 |
|---|---|---|
| A. 模組化單體起步 | 單一程式碼庫、單一部署單位、交易與 Outbox 易保證、模組邊界可用靜態檢查落實 | 單一故障域、擴充粒度較粗 |
| B. 直接拆微服務 | 部署與擴充粒度細、故障隔離 | 分散式交易、跨服務一致性、部署與可觀測性複雜度在起步階段過高；模組介面未穩定就拆分，改介面成本高 |
| C. 單一巨大單體（無模組邊界） | 最簡單 | 違反 SPEC-SOURCE.md §27（不得全塞單一巨大檔案、模組責任邊界清晰）；後期拆分幾乎不可能 |

## 決定

選 A：模組化單體起步。一個 Go Monorepo 程式碼庫，22 個模組各有獨立的 `internal/<模組>` 套件邊界，只經公開介面互相呼叫（見 `MODULE_BOUNDARIES.md`）；部署時 API、Realtime Gateway、Worker 為三個行程角色，由同一程式碼庫建置；資料庫起步為單一 PostgreSQL（邏輯分表、物理同庫）。

## 理由

1. SPEC-SOURCE.md 明文：「初期可模組化單體，不得互相依賴混亂」——起步形態已有定論，本 ADR 只是記錄與落實。
2. 訊息寫入的原子性（業務寫入＋Outbox 同一交易）與 Sequence 分配，在單庫單體內最容易正確保證；拆分後須以分散式機制重做，起步階段不值得。
3. 模組邊界以靜態檢查（import 掃描）落實，拆分時只需把已穩定的公開介面改走 gRPC，資料表歸屬不變（見 `SYSTEM_ARCHITECTURE.md` §4.2 擴充路徑）。
4. 拆分觸發條件已定：某一模組的擴充需求、部署節奏或故障隔離需求與其他模組明顯不同，且其公開介面已穩定；未達條件不得拆分。

## 後果

- Phase 01 須建立模組邊界的靜態檢查（CI 門檻），新增跨模組依賴須先更新 `MODULE_BOUNDARIES.md`。
- 拆分不得改變對外 API 前綴（`/api/v1/*`）與 WebSocket 事件名。
- 本決定不涉及花錢或綁卡；部署成本見 ADR-009。
