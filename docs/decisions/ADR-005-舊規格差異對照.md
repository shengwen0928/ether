# ADR-005：舊 MASTER_SPEC／CONTRACTS 與 NEXUS 規格差異對照

> **品牌更名追溯註記（2026-11-25 00:42 使用者品牌企劃書）：** 本文件中的「NEXUS 規格」指使用者 2026-11-25 00:29 下達的原始規格文件，該文件下達時的品牌暫定名為 NEXUS，現已正式改為 ETHER。本文件為歷史差異對照，內文保留原始寫法僅供追溯；除本註記外，一律以 ETHER 為準。

- **狀態**：已決定（草案／待批准）
- **日期**：2026-11-25（Phase 00）
- **依據**：SPEC-SOURCE.md「既有成果對照」、PLAN.md、MASTER_SPEC.md（v0.1 草案）、CONTRACTS.md（v1 凍結＋v2 增補草案）

## 問題

舊 Kotlin＋Supabase 路線（PLAN.md／MASTER_SPEC.md／CONTRACTS.md）與 NEXUS 規格（2026-11-25 00:29，28 節＋Phase 00–12 手冊）有何差異？舊文件的哪些內容可重用、哪些已被取代？

## 決定

NEXUS 規格取代舊路線的技術決策；舊文件以 SPEC-SOURCE.md §20 表名、§21 事件名與新技術棧為準的部分一律以 NEXUS 為準。舊文件的**功能分析可重用**（需求、邊界條件、驗收思路），**技術合約不可沿用**。舊檔案不得覆蓋、不得刪除，差異以本 ADR 為準。

## 差異表一：技術棧

| 面向 | 舊路線（PLAN／MASTER_SPEC／CONTRACTS） | NEXUS（以 NEXUS 為準） |
|---|---|---|
| 用戶端 | Kotlin＋Android 先行（與 eyecontrol 同技術棧） | Flutter＋Dart（Android／iOS／Windows／macOS／Web 五平台）；React＋TypeScript（Web／Admin） |
| 後端 | Supabase（Auth、Realtime、Storage、Postgres 免費層） | Go（Gin 或 Echo）＋PostgreSQL 自架＋Valkey＋NATS JetStream＋gRPC＋MinIO＋Meilisearch（架構調整後，見 ADR-009） |
| 即時傳輸 | Supabase Realtime 頻道 | WebSocket＋NATS JetStream（見 ADR-006） |
| 通話 | Android 原生 WebRTC，信令走 Supabase Realtime | WebRTC＋LiveKit Community Edition 自架 SFU，信令走 WebSocket Gateway（見 ADR-011） |
| 部署／CI | 本機 harness＋CI（repo 尚未建立） | Docker Compose＋Coolify＋OpenTofu＋GitHub Actions（見 ADR-013）；iOS 走 macOS CI（見 ADR-003） |
| 身分 | Supabase Auth | Keycloak（見 ADR-010） |
| 階段劃分 | Phase 0／1／2／3（三階段） | Phase 00–12（十二階段，手冊 B–N） |

## 差異表二：表名（以 NEXUS §20 為準，不得改名）

| 概念 | 舊路線表名（CONTRACTS v1／MASTER_SPEC） | NEXUS 表名（§20） | 備註 |
|---|---|---|---|
| 使用者主檔 | `profiles`（id＝auth.uid） | `users`（主檔）＋`user_profiles`（公開檔案） | 舊 `profiles` 一表兩責，NEXUS 拆為主檔與檔案 |
| 使用者設定／裝置／Session | （v2 提案 NP-41／42／43／45／52，未定案） | `user_settings`、`user_devices`、`user_sessions`、`user_security_keys` | NEXUS 已定表名，舊提案僅供參考 |
| 好友 | `friendships`（requester／addressee、status pending／accepted／blocked） | `friendships`、`friend_requests`、`blocked_users`、`hidden_users` | 邀請／封鎖／隱藏在 NEXUS 分表，語義不得混為一談 |
| 對話 | `conversations`、`conversation_members` | `conversations`、`conversation_members`、`conversation_settings` | 表名相同，NEXUS 增 `conversation_settings` |
| 訊息 | `messages`（kind text／voice／image／file）、`attachments` | `messages`、`message_receipts`、`message_reactions`、`message_attachments`、`message_replies`、`message_forwards`、`message_pins` | 舊 `attachments` 改為 `message_attachments`；回條／反應／回覆／轉傳／置頂在 NEXUS 分表 |
| 群組／社群 | `conversations`（type group）兼作群組；（公開社群為 NP-23 提案） | `groups` 表組、`communities` 表組（各 5–6 張） | NEXUS 群組與社群為獨立表組，不得以對話表兼作 |
| 媒體 | Storage 路徑存於 `messages.body`／`attachments` | `media_files`、`media_uploads`、`media_thumbnails`、`media_access_logs` | NEXUS 媒體為獨立模組與表組 |
| 貼圖／動態／官方／Bot | NP-27～NP-40 提案表組（未定案） | `sticker_packs` 等、`posts` 表組、`official_accounts` 等、`bot_applications` 等（§20 已定） | 舊 NP 提案不得直接沿用為定案表名 |
| 通話 | NP-09／NP-10／NP-11 提案（`calls` 等） | `calls`、`call_participants`、`call_events` | NEXUS 無品質表（NP-11 不沿用） |
| 管理 | （無） | `admin_users`、`admin_roles`、`admin_permissions`、`admin_audit_logs`、`reports`、`moderation_actions` | NEXUS 管理體系為獨立表組 |

完整 64 張表歸屬見 `MODULE_BOUNDARIES.md` §4；欄位級定義見 ERD 文件（另冊），不得以舊文件的欄位定義代替。

## 差異表三：傳輸層

| 面向 | 舊路線（CONTRACTS v1） | NEXUS（以 NEXUS 為準） |
|---|---|---|
| 頻道 | `chat:<conversation_id>`、`presence:<user_id>`、`call:<conversation_id>`、`friends:`／`sync:`／`account:`（v2 提案） | WebSocket 事件協定（§21 事件名，見下）；頻道概念由 Gateway Registry＋NATS 主題取代，不得沿用 Supabase 頻道名作實作依據 |
| 訊息事件 | `message_created`、`message_edited`、`member_joined`（payload 為列全文） | `message.send`、`message.received`、`message.delivered`、`message.read`、`message.recalled`、`typing.start`、`typing.stop`、`presence.online`、`presence.offline`、`conversation.updated`、`group.member.joined`、`group.member.left`、`call.incoming`、`call.accepted`、`call.ended`（須有事件 ID、時間戳記、版本、關聯識別碼） |
| 送出語義 | `send_message(conversation_id, kind, body)`，30 秒逾時標 failed，重送帶同一 `client_message_id` 去重 | 同一去重與冪等概念，經 Outbox→NATS→Gateway 路徑落實（見 `DATA_FLOW.md` §3）；30 秒逾時值為舊合約已定值，新協定的逾時值由 WebSocket 協定文件定案，不得擅改舊值為新協定值 |
| 排序 | 一律 `(created_at, id)`，不得依客戶端時間 | 排序鐵律概念重用；排序鍵由 ERD／事件協定文件定案（Sequence／Cursor 方向，見 `DATA_FLOW.md`） |
| 通話信令 | `offer`、`answer`、`ice-candidate`、`hangup`，狀態機 IDLE→RINGING→CONNECTED→ENDED | 信令概念重用，事件名以 §21 的 `call.*` 為準；SDP／ICE 交換仍走 WebSocket，不得走 NATS |

## 功能分析重用聲明

以下舊文件內容**可重用為功能分析**（需求細節、邊界條件、驗收思路），重用時須改寫為 NEXUS 的表名、事件名與技術棧，不得原文照搬舊合約名：

- MASTER_SPEC.md 第 1–14 節的功能需求、邊界條件（如編輯／收回時限概念、封鎖語義、投票規則、通話品質概念）與驗收標準思路。
- CONTRACTS.md v2 的 NP 提案索引可作「待定案事項清單」參考，但 NP 表／事件／端點皆為「新增提案」，未經批准不得作為 NEXUS 實作依據（舊文件自身的效力說明亦同）。
- PLAN.md 的誠實紅線（未驗證不宣稱、免費層先講明、原創鐵律）全數重用，NEXUS 版本見 SPEC-SOURCE.md §27。

## 後果

- 新實作不得引用舊表名、舊頻道名或舊函式簽名作依據；引用舊功能分析時須註明來源節次與改寫對照。
- 舊檔案（`~/workspace/messenger-app/`）保持原樣，不得覆蓋、刪除或改寫。
