# ETHER 使用者身分與權限模型（IDENTITY_AND_PERMISSIONS）

> 依據：`SPEC-SOURCE.md` §05（帳號系統）、§06（好友系統）、§08（群組）、§09（社群）、§17（隱私與安全）、§19（Web 管理後台）、§20（資料庫表名）、§21（API 前綴）、手冊 E（Phase 03 身分帳號），以及架構調整指令（2026-11-25 00:33）：身分驗證改 Keycloak。
>
> 表名、API 前綴、事件名以 SPEC-SOURCE 為準，不得改名改義。角色與權限名詞須與 ERD／API 文件將使用的名稱一致：本文件使用的表名為 `users`、`user_profiles`、`user_settings`、`user_devices`、`user_sessions`、`user_security_keys`、`group_roles`、`community_roles`、`admin_users`、`admin_roles`、`admin_permissions`、`admin_audit_logs`，以及好友與聊天相關表（見第 7 節）。Keycloak 概念（Realm／Client／角色）寫入本文件，但 ETHER 業務關聯（使用者／好友／裝置）仍以 §20 表名為準，不得破壞。
>
> 本文件為 Phase 00 架構文件，不構成完成宣告。成本一律「待查證」。未決事項只列問題，不代決定。

## 1. 總則

1. 所有重要資料操作必須經過後端驗證；重要商業邏輯不得只寫在前端；管理員權限不得由前端自行判斷。
2. 權限檢查點一律在後端強制：每個 API 端點與 WebSocket 事件處理器，在執行商業邏輯之前，須先驗證身分（Authentication）與授權（Authorization）；前端的權限顯示僅為使用者體驗，不得作為授權依據。
3. 權限失敗時，後端須回傳明確的授權錯誤，不得以靜默失敗、空結果或錯誤訊息差異洩漏不應揭露的資訊（例如帳號存在性、封鎖狀態）。
4. 敏感操作須留存稽核軌跡；管理員操作一律寫入 `admin_audit_logs`，社群與群組的管理操作留存操作紀錄。
5. 本文件不自發明加密演算法；E2EE 金鑰與身分的關係見第 8 節，加密協定細節見 `docs/security/E2EE_RESEARCH.md`。

## 2. 帳號生命週期

帳號生命週期以 `users` 表為主體，公開顯示資料以 `user_profiles` 表承載，個人設定以 `user_settings` 表承載。

| 階段 | 說明 | 相關表 |
|---|---|---|
| 註冊申請 | 使用者以手機號碼、Email 或 OAuth（Google、Apple）提出註冊，須同意條款與隱私政策，同意紀錄須留存（含政策版本） | `users`、`user_profiles` |
| 驗證 | 手機 OTP 或 Email 驗證；OTP 供應商待決定（未決問題 NQ-02），成本：待查證；驗證逾時與重發有明確狀態與 Rate Limit | `users`（驗證狀態欄位，欄位名待 ERD 定案） |
| 啟用 | 驗證通過後帳號啟用，可登入；未驗證帳號不得存取需授權的功能 | `users` |
| 正常使用 | 登入、發訊、加好友、建群組、通話等，皆須經身分與權限檢查 | 全部業務表 |
| 停用 | 使用者可申請停用，或管理員可停權；停用期間不得登入，已發出的 Token 須撤銷；停用原因與期限留存紀錄 | `users`、`admin_audit_logs`（管理員停權） |
| 刪除申請 | 使用者可申請刪除帳號，含冷靜期與進度查詢；冷靜期天數待定（OQ-03 相關）；冷靜期內登入即取消刪除申請 | `users`（刪除申請狀態，表名待 ERD 定案，方向承接 MASTER_SPEC 的刪除申請表概念，以 ETHER §20 為準） |
| 刪除完成 | 冷靜期屆滿後刪除流程開始，刪除完成後不得恢復；個人檔案、好友關係、動態貼文依資料保存政策處理，訊息列的處理須符合 append-only 與法規的雙重要求，具體方式待合約修訂時定案 | 保存政策表（待 ERD 定案） |
| 資料匯出 | 使用者可申請匯出個人資料，匯出範圍由使用者選擇，匯出檔案須在期限內提供下載（期限待定），狀態可查詢 | 匯出紀錄（表名待 ERD 定案） |

補充規則：

- 一個自然人可擁有的帳號數量、帳號合併與轉移規則，尚未定案，列為規格缺口。
- 未成年人帳號的年齡門檻與法定代理人同意方式待法律意見確認（OQ-13）；門檻未確認前，不得以自行推測的年齡判定未成年人身份。
- 帳號刪除後，唯一 ID 是否可被重新註冊、重新註冊的冷卻規則，尚未定案，列為規格缺口。

## 3. 身分驗證：Keycloak（Realm／Client／角色）＋ OAuth 2.0／OIDC＋PKCE

身分驗證改由 Keycloak 承擔。Keycloak 為自架開源身分與存取管理服務，部署走 Docker Compose＋Coolify，憑證以 OpenBao 管理，部署驗證為「待 CI 或有 Docker 的環境驗證」，此 VM 無 docker，不得寫已驗證。

### 3.1 Keycloak 概念與 ETHER 對應

| Keycloak 概念 | ETHER 用法（方向，待 ERD／部署文件定案） |
|---|---|
| Realm | ETHER 使用者身分的隔離邊界；一般使用者與管理員使用不同 Realm（或以 Client 與角色嚴格隔離，隔離方式待定案），不得共用同一身分邊界而互相越權 |
| Client | 每個應用端（行動 App、桌面、Web、Admin）對應各自的 Client；Client 須設定正確的重新導向 URI 與授權類型，不得使用不安全的隱式流程；Client Secret 不得寫入原始碼或前端可讀取的設定 |
| User | Keycloak 中的身分主體，對應 ETHER `users` 表的一列；對應關係以穩定的外部識別碼綁定，不得僅以 Email 字串比對作為唯一綁定依據（綁定欄位待 ERD 定案） |
| Role（Realm Role／Client Role） | Keycloak 角色僅作為身分層的粗粒度角色（例如一般使用者、管理員登入資格），業務細粒度權限（群組 Owner／Admin／Member、社群分級、管理員權限項）仍以 ETHER `group_roles`／`community_roles`／`admin_permissions` 為準，不得以 Keycloak 角色代替業務權限檢查 |
| Identity Provider | Google、Apple 等外部 OAuth／OIDC 提供者，經 Keycloak 整合為 Identity Provider；首次登入須補齊必要個資與同意紀錄 |

### 3.2 保留的流程（不得刪減）

- Email 註冊驗證：Email 註冊須經 Keycloak 的 Email 驗證流程，驗證信逾時與重發有明確狀態與 Rate Limit；未驗證帳號不得存取需授權的功能。
- 登入與登出：手機／Email／密碼／驗證碼、Google、Apple 登入皆經 Keycloak；登出須同時撤銷 Keycloak Session 與 ETHER `user_sessions`，不得只清前端狀態。
- OAuth：Google 與 Apple 登入走 OAuth 2.0／OIDC，授權碼流程須使用 PKCE，不得使用不安全的隱式流程。
- MFA：MFA 由 Keycloak 的驗證流程承擔（見第 6 節），第二因素方式待決定（OQ-04）。
- Session：Keycloak Session 與 ETHER `user_sessions` 須同步撤銷（見第 4、5 節）；遠端登出須同時撤銷兩者。
- Access／Refresh Token：Token 由 Keycloak 簽發，ETHER 後端驗證簽名與有效期（見第 4 節）；Refresh Token Rotation 規則保留。
- 裝置管理與遠端登出：裝置以 `user_devices` 表承載（見第 5 節），遠端登出即時生效。
- 密碼重設：密碼重設走 Keycloak 的重設流程，須經 Email／手機驗證；重設後舊 Session 與 Refresh Token 須撤銷（見第 4 節）。

### 3.3 不得破壞的關聯

- Keycloak 的引入不得破壞 `users` 與 `user_profiles`、`user_settings`、`user_devices`、`user_sessions`、`user_security_keys` 的關聯，不得破壞好友關係（`friendships`／`friend_requests` 方向，以 §20 為準）、群組成員與社群成員關聯。
- 業務授權檢查一律以 ETHER 資料庫當下狀態為準，不得僅以 Keycloak Token 內的角色聲明作為業務授權依據；Token 內的角色聲明僅供身分層參考，業務權限須以後端查詢為準。
- 帳號停用、刪除、匯出等生命週期操作，須同時處理 Keycloak 身分與 ETHER 業務資料，兩邊狀態不得長期不一致；同步失敗時須有明確錯誤與補償流程，待定案。

### 3.4 認證細節

- 首次 OAuth 登入須補齊必要個資與同意紀錄；已存在帳號的 OAuth 綁定，須經已登入狀態下的綁定流程，不得僅憑 OAuth 身份直接接管既有帳號。
- OAuth 憑證（Client ID、Client Secret）不得寫入原始碼，不得寫入前端可讀取的設定；Production Secrets 不入 Git，以 OpenBao 與環境變數管理為準。
- OAuth 提供者的帳號與 ETHER 帳號的對應關係，須留存對應紀錄以供解綁與稽核；解綁後不得影響 ETHER 帳號本身的登入能力（若尚有其他登入方式）。
- 登入失敗、授權失敗、PKCE 驗證失敗，皆須回傳明確錯誤，不得洩漏提供者端的敏感資訊。

## 4. Token：短效 Access Token＋Refresh Token Rotation（Keycloak 簽發）

Token 由 Keycloak 簽發，ETHER 後端驗證 Token 簽名、簽發者、有效期與撤銷狀態；ETHER 業務 Session 仍以 `user_sessions` 表承載，兩者撤銷須同步。

| Token | 性質 | 規則 |
|---|---|---|
| Access Token | 短效 | 有效期短，須以安全方式傳輸（HTTPS，Authorization 標頭）；不得以 URL 查詢參數傳遞；不得存於可被第三方腳本讀取的位置（Web 端儲存方式以安全架構文件為準） |
| Refresh Token | 長效、可撤銷、可輪換 | 每次使用後輪換（Rotation），舊 Refresh Token 即失效；Refresh Token 須以雜湊或等效安全方式儲存，不得明文儲存；盜用偵測（重放已輪換的 Refresh Token）須觸發 Session 撤銷與安全通知，具體規則待安全架構文件定案 |
| Session | 伺服器端會話 | 以 `user_sessions` 表承載，含裝置、登入時間、最後活動時間、撤銷狀態；Session 可查看、可撤銷；遠端登出即時生效 |

規則：

- Token 竊取防護：Token 不得寫入日誌、錯誤訊息或前端可讀取的持久化明文；Token 洩漏時須可撤銷，不得僅靠有效期等待過期。
- 登出時，Keycloak Session 與 ETHER Session、Access Token 與 Refresh Token 皆須撤銷；改密與密碼重設後，舊 Session 與 Refresh Token 須撤銷。
- 多裝置各有獨立 Session，撤銷某一裝置的 Session 不得影響其他裝置（除非使用者選擇登出全部裝置）。
- API 呼叫須攜帶有效的 Access Token；Token 過期時以前端 Refresh 流程換取新 Token，Refresh 失敗時導向重新登入，不得以靜默失敗繼續操作。

## 5. Session／裝置信任

- 裝置以 `user_devices` 表承載：裝置名稱、平台、最後活動時間、登入時間、撤銷狀態。使用者可查看登入裝置清單，可遠端登出任一裝置；遠端登出後，該裝置的本機資料須清除、存取權杖失效、推播權杖一併失效，不得繼續同步新訊息。
- 裝置信任：新裝置登入有紀錄；異常登入有安全通知；裝置信任狀態可管理（信任／不信任）；受信任裝置的生物辨識快速登入，須以裝置端安全儲存為前提，生物特徵不得上傳伺服器。
- 裝置數量上限待定；超過上限的新裝置登入時，須提示使用者選擇登出舊裝置，不得靜默踢掉舊裝置。
- 離線超過一段時間的裝置，上線時須重新驗證身份，不得直接同步（期間待定，承接 MASTER_SPEC 第 10 節方向，ETHER 定案待定）。
- Session 撤銷須即時生效，不得等待該裝置下次連線才生效；撤銷後該裝置的本機資料清除，須以裝置端確認為準，伺服器端不得宣稱已清除未連線裝置的本機資料。

## 6. MFA（雙重驗證，經 Keycloak 驗證流程）

- 使用者可開啟／關閉 MFA；開啟後登入時除密碼外須通過第二因素驗證；MFA 驗證流程由 Keycloak 承擔，ETHER 後端驗證 MFA 已通過的 Token 聲明，不得僅憑前端聲明放行。
- 第二因素的方式待決定（OQ-04）：例如簡訊驗證碼、驗證器應用程式、Email 驗證碼或其他方式；本文件不代決定。
- 第二因素的密鑰與備用碼，須以 `user_security_keys` 表或等效安全儲存承載（表名以 §20 為準，欄位設計待 ERD 定案）；密鑰與備用碼明文不得存入資料庫；備用碼明文只顯示一次，用過即失效，不得重複使用。
- 關閉 MFA 須通過第二因素驗證，不得僅憑密碼關閉；第二因素驗證失敗超過次數時，帳號暫時鎖定（次數與鎖定時間待定）。
- MFA 設定變更須留存紀錄，並通知使用者（安全通知）。

## 7. 角色模型

角色分為四層，層與層之間不得混用：一般使用者角色、群組角色、社群角色、管理員角色。角色名詞與 ERD／API 文件一致。

### 7.1 一般使用者（無全域特權）

- 每位註冊使用者皆為一般使用者，預設無任何管理特權。使用者只能存取自己有權存取的資料，權限檢查以好友關係、群組成員身份、社群成員身份、封鎖規則與隱私設定為準。
- 使用者之間的關係狀態（好友／封鎖／隱藏）為單向或雙向關係，不得混為一談：刪除、封鎖、隱藏是不同狀態，須分開建模。

### 7.2 群組角色（`group_roles`）

群組角色適用於單一群組，角色名詞：Owner、Admin、Member。

| 角色 | 說明 |
|---|---|
| Owner | 群組建立者或所有權受讓人；唯一可轉移所有權與解散群組的角色；擁有全部群組管理權限 |
| Admin | 群組管理員；可新增／移除成員、改名、換頭像、發佈公告、管理邀請、管理成員、部分權限管理；不得轉移所有權、不得解散群組、不得移除 Owner |
| Member | 一般成員；可傳送訊息、發起投票、上傳媒體、@成員、查看公告；不得執行管理操作 |

- 群組角色的權限對照表，以 `group_roles` 表承載；權限檢查在後端，請求當下判定，不得以快取的舊權限放行。
- 權限變更即時生效，不得要求重新加入；成員被移除後，不得再存取群組的新訊息，歷史訊息查看權限依退出規則處理。

### 7.3 社群角色（`community_roles`）

社群採分級權限，角色名詞以 `community_roles` 表為準。SPEC-SOURCE §09 要求「分級權限與操作紀錄」，但具體等級劃分尚未定案，本文件只定框架，不代定等級：

- 框架：社群建立者為最高級；其下設管理層級與一般成員層級；管理操作（成員管理、公告、規則、檢舉處理、黑名單、多聊天室管理）須有操作紀錄。
- 具體等級名稱、等級數量、各等級的操作對照表，待使用者決定後寫入 ERD 與 API 文件，列為規格缺口。
- 社群角色不得與群組角色混用；同一使用者在不同社群可有不同角色，在同一社群內僅有一個角色。

### 7.4 管理員角色（`admin_users`、`admin_roles`、`admin_permissions`）

管理後台的管理員，與一般使用者帳號分離，獨立認證與權限。

| 概念 | 說明 |
|---|---|
| `admin_users` | 管理員帳號表；管理員登入走獨立的管理員認證流程（Keycloak 獨立 Realm 或嚴格隔離的 Client／角色，隔離方式待定案），不得以一般使用者 Token 存取管理後台 API |
| `admin_roles` | 管理員角色表；角色名詞待定案（例如超級管理員、內容審核員、客服、系統維運等方向，具體名稱與數量待決定） |
| `admin_permissions` | 管理員權限表；權限項列舉待定案（例如使用者停權、檢舉審核、貼圖上架、系統監控等方向，具體權限項待決定） |
| `admin_audit_logs` | 管理員操作稽核表；每次管理員操作皆須寫入，含操作者、操作對象、操作內容、時間，不得遺漏，不得事後修改 |

規則：

- 管理員權限採最小權限原則：管理員僅能執行其角色被授予的權限，不得越權；權限檢查在後端強制，前端不得自判。
- 管理員不得任意讀取 E2EE 訊息；管理員不得讀取使用者的私密個資超出最小必要範圍；檢舉內容的存取權限須最小化。
- 管理員帳號的建立、角色授予、權限變更、停用，皆須留存稽核軌跡，並由具備相應權限的管理員執行，不得由一般使用者或前端操作完成。

### 7.5 官方帳號與 Bot 的身分

- 官方帳號以 `official_accounts` 表承載，認證標章僅在認證通過後顯示；官方帳號的代表身份不得以個人使用者的身份偽裝。
- Bot 以 `bot_applications`／`bot_webhooks`／`bot_events` 表承載（§20 表名）；Bot API 以金鑰認證，金鑰須可撤銷、可輪換，明文只顯示一次；Bot 回覆須標示為機器人，不得偽裝真人。
- Bot 的權限受 API 權限約束，不得超出其被授予的事件訂閱與操作範圍。

## 8. 權限檢查點（後端強制、前端不得自判）

每個業務操作，後端在執行前須完成下列檢查（順序為方向，具體實作以 API 文件為準）：

1. **身分驗證**：Access Token 有效、未撤銷、未過期；Session 有效；裝置未被撤銷。
2. **帳號狀態**：帳號未停用、未刪除、未鎖定；MFA 驗證（如適用）已通過。
3. **關係與成員身份**：好友關係、群組成員身份、社群成員身份、官方帳號關注狀態，皆以資料庫當下狀態為準。
4. **角色與權限**：群組角色（`group_roles`）、社群角色（`community_roles`）、管理員權限（`admin_permissions`），皆以後端授權檢查為準。
5. **隱私與封鎖**：隱私設定（誰可加好友／搜尋／看檔案／看動態／傳訊息／加群組、是否公開上線／已讀／生日）與封鎖規則，皆須在後端檢查；被封鎖者不得以任何路徑繞過封鎖存取內容。
6. **資源所有權**：訊息編輯／收回僅限傳送者、貼文編輯／刪除僅限作者、檔案下載僅限有權存取對話的成員，皆以後端檢查為準。
7. **Rate Limit 與防濫用**：發送頻率、登入嘗試、驗證碼重發、檢舉頻率等，皆以後端 Rate Limit 強制，不得僅靠前端節流。

前端的角色是：依後端回傳的權限資訊顯示或隱藏操作入口、提供友善的錯誤提示；前端不得自行判定權限、不得以隱藏入口代替後端檢查、不得以快取的舊權限放行。

## 9. E2EE 裝置金鑰與身分的關係

- 每裝置獨立金鑰：每台裝置有獨立的身分金鑰與訊息金鑰，裝置之間不共用私鑰；私鑰一律只存於裝置本機（安全儲存），不得上傳伺服器。
- 身分金鑰與使用者帳號的綁定：身分金鑰的公鑰部分與使用者帳號關聯，伺服器僅儲存公鑰與一次性預共享金鑰的公鑰部分，不得儲存私鑰或訊息明文。
- 裝置撤銷：裝置被撤銷（遠端登出、裝置遺失、使用者主動撤銷）時，該裝置的金鑰須失效，不得再解密新訊息；撤銷須即時生效於伺服器端，裝置端的本機金鑰清除以裝置端確認為準。
- 新裝置驗證：新裝置加入時，須經既有裝置確認或帳號驗證（驗證方式待定案，見 E2EE 研究文件），不得僅憑電話號碼或公開識別完成金鑰移轉；新裝置的安全金鑰驗證（Safety Number 方向）須可供使用者比對。
- 金鑰備份：金鑰備份方案的比較與風險見 `docs/security/E2EE_RESEARCH.md`；備份方案未定案前，不得宣稱金鑰可安全備份或恢復。
- 管理員與 E2EE：管理員不得任意讀取 E2EE 訊息；伺服器不得明文儲存或讀取 E2EE 訊息；E2EE 與一般聊天室的功能差異須在介面明確標示。
- 加密協定本身（Signal Protocol、Double Ratchet、X3DH 等）見 E2EE 研究文件；本文件不自發明加密演算法，不宣稱已選定未經使用者批准的實作。

## 10. 隱私控制與檢舉封鎖的權限含義

- 隱私控制（§17）：誰可加好友／搜尋／看檔案／看動態／傳訊息／加群組、是否公開上線／已讀／生日、是否允許聯絡人同步，皆為使用者級設定，以 `user_settings` 表方向承載（欄位設計待 ERD 定案）；設定變更即時生效於後端檢查。
- 檢舉封鎖：檢舉者身份不對被檢舉者揭露；被封鎖者無法傳訊、發起通話、查看動態，亦無法得知自己被封鎖；封鎖即時生效；檢舉與封鎖的權限檢查，皆在後端強制。
- 搜尋權限：搜尋結果須遵守存取權限與封鎖規則，不得回傳無權存取的內容。

## 11. API 前綴與事件名的權限含義

- API 前綴以 §21 為準：`/api/v1/auth`、`/users`、`/profiles`、`/friends`、`/contacts`、`/conversations`、`/messages`、`/groups`、`/communities`、`/media`、`/stickers`、`/posts`、`/calls`、`/notifications`、`/search`、`/official-accounts`、`/bots`、`/admin`。其中 `/admin` 僅限管理員 Token 存取，一般使用者 Token 不得存取。
- WebSocket 事件名以 §21 為準；每個事件處理器在分發前，須驗證訂閱者的身分與對該對話／群組／社群的存取權限，不得向無權訂閱者分發事件。
- 錯誤碼規範與 API 命名規範，見 `docs/api/API_STANDARDS.md`（Phase 00 另一文件工人負責，本文件不代寫）。
