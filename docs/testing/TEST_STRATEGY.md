## 2. 測試原則

1. 未驗證不宣稱：沒有實機／實際驗證、沒有測試證據的功能，一律標「未驗證」，不得宣稱已完成、已上線、已驗證。編譯通過、CI 通過、純邏輯 harness 通過，皆不等於實機驗證。
2. 真實驗收：最終驗收以真實裝置、真實帳號、真實後端、真實資料為準（§28）；不允許單機假聊天、Mock API、靜態 UI、假按鈕宣稱完成。
3. 每功能須有 UI、狀態管理、API、資料庫、權限驗證、錯誤處理、測試、文件（手冊 A）；缺任一項不得標完成。
4. 每階段須提供：完成功能、新增／修改檔案、DB 變更、API 變更、測試結果、未完成項、已知問題、下一階段（§27）。測試結果須附證據（日誌、截圖、錄影、訊息識別碼等），不得僅寫「通過」。
5. 安全性測試不得以「規格文字」代替證據；加密、刪除、權限等宣稱須以實作與測試證據為準。
6. 測試不得破壞正式資料：測試一律在隔離環境進行，不得在正式環境以真實使用者資料測試；正式環境的驗證演練須在隔離環境進行（見 §7）。
7. 缺陷須可追溯：缺陷記錄須含重現步驟、環境、版本、證據、影響範圍，不得以「已修復」結案而不附回歸測試證據。

## 3. 測試金字塔與五層

測試金字塔（草案方向，比例不預寫數字）：底層多、頂層少；Unit 最多、E2E 最少且最貴。五層定義如下，缺一不可：

### 3.1 Unit（單元測試）

- 範圍：核心商業邏輯（訊息狀態機、好友狀態機、群組權限判定、去重邏輯、Sequence 分配、Cursor 分頁邏輯、錯誤碼對映、輸入驗證規則等）。純邏輯模組須無外部依賴、可在 harness 中測試。
- 方法：各語言的標準單元測試框架（Flutter／Dart、Go，框架選定待 Phase 01 定稿）；測試須覆蓋正常、邊界、異常三類輸入，不得僅測正常路徑。
- 隔離：不得依賴資料庫、網路、檔案系統、時間（時間須可注入，不得以系統時間假設）；外部依賴須以介面隔離，不得在單元測試中直連真實服務。
- 驗收寫法：見 §8；覆蓋率門檻不預寫數字，門檻值與計算方式待定稿（覆蓋率不得作為唯一品質指標，須併看邊界覆蓋）。

### 3.2 Integration（整合測試）

- 範圍：API／資料庫（PostgreSQL＋Migration）／Valkey／WebSocket／訊息（NATS JetStream）／媒體（MinIO）／推播（FCM／APNs，測試模式）／搜尋（Meilisearch）／身分（Keycloak，測試 Realm）／通話（LiveKit CE，測試房間）。
- 方法：以 Docker Compose 啟動真實依賴（待 CI 或有 Docker 的環境驗證，此 VM 無 docker，不得寫已驗證）；測試資料庫須為獨立測試庫，不得共用開發庫、不得共用正式庫；每個測試案例須可獨立重跑，不得依賴執行順序。
- 重點：FK／唯一約束、Migration 向前／回滾、事務邊界（Transactional Outbox，如採用）、冪等去重、WebSocket 連線／重連／恢復、媒體上傳／掃描／存取權限、推播投遞與去重、搜尋索引同步與權限過濾。
- 外部服務：推播、簡訊 OTP、外部 AI API、商店支付等，整合測試須以測試模式／沙箱／可驗證的測試替身進行，替身的使用範圍須在測試文件中明定，不得以替身結果冒充真實服務驗證（真實服務驗證見 §3.3 E2E 與 §7）。

### 3.3 E2E（端對端測試，§24 12 步）

- 範圍：§24 所定的 12 步完整流程，一字不得改、不得刪減、不得以單機假資料代替：

  1. 註冊 → 2. 登入 → 3. 加好友 → 4. 傳訊 → 5. 收訊 → 6. 傳照片 → 7. 建群組 → 8. 邀成員 → 9. 群組訊息 → 10. 通話 → 11. 推播 → 12. 登出

- 方法：真實裝置與真實帳號（見 §5）；兩台以上不同裝置、不同網路（見 §5.2）；真實後端、真實資料庫、真實物件儲存、真實推播、真實通話（LiveKit CE 自架，待有 Docker 的環境驗證）。
- 擴充：12 步之外，各階段的 E2E 須覆蓋該階段的驗收場景（離線／重連／去重／順序／已讀／多裝置／重啟恢復、媒體互傳、群組管理、社群互動、貼圖／動態、官方帳號／Bot、管理後台操作等），擴充場景在各階段測試文件中定稿，不得以 12 步代替全部 E2E。
- 證據：每步須有可查證據（訊息識別碼、截圖／錄影、伺服器日誌、推播投遞紀錄、通話紀錄等），證據須留存，不得僅寫文字聲明。

### 3.4 Security（安全測試）

- 範圍（§24）：權限繞過、Token 竊取、SQL Injection、XSS、Rate Limit、非法檔案上傳、未授權讀取、帳號接管。另含：CSRF、防暴力破解、Session 固定／劫持、裝置撤銷、E2EE 金鑰管理、Secrets 洩漏、依賴漏洞、API 授權矩陣（每端點×每角色）、封鎖規則不可區分性、檢舉者身份保護、管理員不得讀取 E2EE 訊息。
- 方法：威脅建模（待安全性架構文件定稿）、SAST／DAST、Dependency Scan、Secrets Scan、權限矩陣測試、手動滲透測試（範圍與頻率待定稿）、E2EE 協定審查（Protocol Audit，見手冊 M）。
- 原則：安全測試的發現須分級（嚴重程度待定稿），嚴重發現未修復不得標階段完成；安全測試不得在正式環境以真實資料進行攻擊測試。
- 工具選型：SAST／DAST／Dependency Scan 的工具選定待 Phase 11 定稿，不得預寫工具名為已定；錯誤追蹤以 GlitchTip 自架，不得將安全測試的敏感發現上傳至未經批准的第三方服務。

### 3.5 Performance（效能測試）

- 範圍（§24）：延遲、WebSocket 連線數、吞吐量、API 回應、資料庫負載、媒體上傳。另含：大型群組廣播、搜尋併發、通話品質（延遲、封包遺失、抖動，見 Phase 07 文件）、App 記憶體／CPU、電池／流量（背景連線）。
- 方法：壓力測試須在隔離的壓測環境進行（待 CI 或有 Docker 的環境驗證），以可重現的壓測腳本與資料集進行；壓測資料集須為虛構資料，不得用真實使用者資料。
- 禁忌：不得在無壓力測試下宣稱可承載特定同時在線數（§23）。效能門檻（延遲、吞吐量、連線數）一律待壓測後以實測數據定為暫定值，不得在本文件預寫；門檻的寫法見 §8。
- 監控：壓測期間須以 Prometheus＋Grafana＋Loki 監控 API、WebSocket、資料庫、Worker、Media、AI 的指標（見部署文件），壓測報告須附監控截圖／匯出，不得僅寫結論。

## 4. 測試資料與隔離

- 測試資料一律使用虛構人名、虛構群組名、原創測試圖片，不得使用第三方商標、品牌名稱、受保護素材，不得使用真實使用者資料。
- 環境隔離：開發、測試、staging、production 四環境分離（環境劃分見部署文件）；測試資料庫、測試 Keycloak Realm、測試 MinIO Bucket、測試 Meilisearch 索引、測試 NATS Stream，皆須與正式環境分離，不得共用。
- 資料隔離：每個測試案例須自備資料、測試後清理（或以事務回滾、獨立 Schema 隔離），不得依賴其他案例留下的資料；並行測試不得互相干擾。
- 敏感資料：測試資料不得含真實密碼、Token、金鑰、電話、Email；測試帳號的憑證須以 Secrets／環境變數注入（OpenBao，見部署文件），不得寫死在測試程式碼或文件中。
- Seed 資料：僅供開發／測試，須冪等、須標示環境，見 ERD.md §9.2；Seed 不得作為 E2E 驗收的替代。

## 5. WS 與通話測試方法

### 5.1 WebSocket 測試

- 單元層：事件信封解析、Sequence 排序、去重邏輯、ACK 狀態機，以純邏輯測試覆蓋。
- 整合層：以真實 WebSocket 伺服器（Go 後端＋NATS JetStream＋Valkey，待有 Docker 的環境驗證）測試連線認證、Heartbeat、重連、恢復、多裝置 Session、限流、Backpressure；以故障注入（斷網、伺服器重啟、快速切網、App 背景／被終止）驗證恢復無遺失、無重複、無亂序。
- E2E 層：兩台真實裝置即時交換訊息，驗證即時／離線／重連／去重／順序／已讀／多裝置／重啟恢復（手冊 G 驗收），證據見 §3.3。
- 工具：WebSocket 測試客戶端的選定待 Phase 05 定稿；測試須能模擬多裝置、多對話、大型群組扇出，不得以單一連線測試冒充併發驗證。

### 5.2 通話測試

- 通話測試一律以真實通話驗證：不同網路、不同平台、真實裝置，WebRTC＋LiveKit CE 自架（待有 Docker 的環境驗證，不得寫已驗證；TURN 頻寬與公網部署需求須特別評估，見部署文件）。
- 覆蓋：一對一語音／視訊、多人、來電／接／拒／忙線、靜音／鏡頭切換、螢幕分享、參與者管理、主持人、紀錄、品質監測、重連、Android 背景來電、iOS CallKit、桌面原生通知、Web 權限處理（平台覆蓋見 PLATFORM_MATRIX.md，另冊）。
- 品質指標：延遲、封包遺失、抖動、解析度變化的記錄與摘要，須以實測數據驗證，不得以模擬畫面、靜態 UI 冒充通話。
- 不得模擬：通話畫面、通話音訊、通話品質摘要，皆不得以模擬代替真實通話驗證。

## 6. 真實裝置與真實帳號（E2E 鐵律）

- E2E 須真實裝置與真實帳號，禁單機假資料：不得以單機模擬器／單一裝置上的兩個客戶端冒充兩台裝置；不得以固定假資料、Mock API、靜態 UI 冒充即時訊息；不得以同一裝置的兩個帳號切換冒充多裝置同步。
- 裝置覆蓋：Android、iOS、Windows、macOS、Web 五平台的 E2E 覆蓋，待各階段定稿（iOS 建置在 Linux 上不可能，須走 macOS CI runner，見 SPEC-SOURCE.md 環境實情；CI 驗證見 §7）。
- 帳號覆蓋：E2E 須以多個真實測試帳號進行（帳號數按場景定稿，例如兩帳號互加好友、三帳號以上群組互動），測試帳號須為測試環境專用，不得用正式帳號、不得用真實使用者帳號。
- 網路覆蓋：Wi-Fi、行動網路、弱網（限速／丟包模擬）、斷網／重連、快速切網，皆須覆蓋；弱網模擬的參數待定稿，不得預寫。
- 證據留存：裝置型號、系統版本、App 版本、網路條件、測試時間、操作錄影／截圖，皆須留存；證據缺失的 E2E 不得標通過。

## 7. CI／CD 與測試環境

- CI 為 GitHub Actions：每次提交／PR 須自動執行靜態分析、單元測試、整合測試（待 CI 或有 Docker 的環境驗證）、OpenAPI 一致性檢查、Secrets Scan、依賴掃描；CI 失敗不得合併，合併規則待 Phase 01 定稿。
- 測試環境：以 Docker Compose＋Coolify 啟動（見部署文件與 SELF_HOSTING.md），服務含 api、realtime-gateway、worker、postgresql、valkey、nats、minio、meilisearch、openbao、keycloak、traefik、prometheus、grafana、loki、glitchtip、livekit、ollama（服務清單見 docker-compose.yml，尚待有 Docker 的環境驗證，不得寫已驗證）。
- 本機 VM 無 docker、無 flutter、無 go（SPEC-SOURCE.md 環境實情）：本地驗證待環境就緒；本文件不假裝本地已驗證，驗證一律寫「待 CI 或有 Docker 的環境驗證」。
- 部署驗證：staging 部署後須執行冒煙測試（健康檢查、註冊登入、訊息收發、媒體上傳、搜尋、通話信令），冒煙失敗不得發布；發布流程與回滾見 ROADMAP.md。
- 錯誤追蹤：測試與 staging／production 的錯誤以 GlitchTip 自架追蹤（見部署文件）；測試失敗的錯誤報告須附 `request_id`、版本、環境，不得附敏感資料。

## 8. 驗收門檻寫法（如何驗、不預寫通過結果）

驗收門檻的寫法規則（本文件只定寫法，不寫通過結果）：

1. 每項驗收須寫：驗收場景、輸入／前置條件、操作步驟、預期可觀察結果、證據形式、判定者（測試人員／自動化）。不得只寫「功能正常」「測試通過」。
2. 數量型門檻（覆蓋率、延遲、吞吐量、連線數、成功率）須寫：量測方法、量測環境、資料集、量測次數、判定公式；門檻值在首次實測前寫「待實測後定為暫定值」，實測後以實測數據覆核，不得在本文件預寫數字。
3. 通過結果不得預寫：驗收文件須留空「實際結果」「證據連結」「判定日期」「判定者」欄位，待驗收執行時填寫；已填寫的結果須附證據，不得空口填寫。
4. 失敗處理：驗收失敗時，須記錄缺陷、影響範圍、修復與回歸測試計畫，不得以「已知問題」掩蓋未通過的驗收而不列入下一階段。
5. 階段門檻：每階段完成後停止審查（見 ROADMAP.md），審查須逐項核對本階段的驗收門檻與證據，未通過者不得進入下一階段，不得以「後階段再補」放行本階段的驗收。
6. 最終稽核：Phase 12 最終稽核逐項比對 PRD、功能矩陣、API、DB、前端、實測，檢查 15 項（手冊 N），完成度以實際驗收為準，不得因階段執行完就判定完成。
