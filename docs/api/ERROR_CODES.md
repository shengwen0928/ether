# ETHER 錯誤碼規範（ERROR_CODES.md）

## 1. 依據與效力

- 本文件以 `~/workspace/ether/SPEC-SOURCE.md` §21 為最高準據，須與 `API_STANDARDS.md`、 `WEBSOCKET_PROTOCOL.md` 一致，不得衝突。API 前綴以 §21 為準（18 個前綴，見 API_STANDARDS.md §2）；WebSocket 事件名以 §21 為準（15 個事件，見 WEBSOCKET_PROTOCOL.md）。
- 本文件定錯誤碼格式、通用碼、領域碼段劃分、錯誤回應格式與客戶端處理原則。個別端點可回傳的錯誤碼清單，須在各端點的 OpenAPI 文件中逐項定稿；本文件不定稿任何個別端點的專屬錯誤碼，不得以本文件的示例為已定合約。
- 不得編造額度、數字、效能指標。限流數值、重試次數、退避間隔等，一律寫「待定稿／待查證」，不得預寫具體數字。舊規格中的數字（如 30 秒逾時）為舊路線已定值，不得直接搬入而不經定稿。
- 架構調整（2026-11-25 00:33 使用者指令，優先於舊技術棧）：邊緣閘道為 Traefik、身分提供者為 Keycloak、監控與錯誤追蹤見部署文件。錯誤碼規範本身不變；舊付費服務名不得殘留。

## 2. 錯誤碼格式

### 2.1 機器可讀錯誤碼

錯誤碼為字串，格式（草案，待定稿確認）：

```
ETHER_<領域>_<具體錯誤>
```

- 全大寫英文字母、數字、底線組成；領域段見 §4；具體錯誤段以簡短動詞／名詞表達，不得含空格、連字號、中文。
- 錯誤碼須穩定：同一語義在各版本、各端點須用同一錯誤碼，不得以不同錯誤碼表達同一語義；錯誤碼一經發布，不得改義、不得重用已廢棄的錯誤碼表達新語義（廢棄規則見 §7）。
- 錯誤碼須與 HTTP 狀態碼搭配使用（見 §3），不得以錯誤碼代替 HTTP 狀態碼；客戶端須同時判讀兩者，不得僅判讀其一。

### 2.2 錯誤碼示例（形式示例，非已定清單）

- `ETHER_AUTH_UNAUTHENTICATED`（未認證）
- `ETHER_AUTH_FORBIDDEN`（無權限）
- `ETHER_VALIDATION_INVALID_FIELD`（欄位驗證失敗）
- `ETHER_COMMON_NOT_FOUND`（資源不存在）
- `ETHER_COMMON_CONFLICT`（狀態衝突）

示例僅說明格式，是否定稿為通用碼見 §3；個別領域的具體錯誤碼見 §4 的碼段劃分，逐碼定稿工作在各階段進行。

### 2.3 人類可讀訊息

- 錯誤回應含人類可讀訊息（`message`，見 §5），語言以繁體中文為預設（草案），多語系訊息的提供方式待定稿。訊息僅供顯示與除錯，不得作為客戶端判讀依據；判讀一律以錯誤碼為準。
- 訊息不得含敏感資訊（密碼、Token、金鑰、內部路徑、堆疊追蹤、資料庫錯誤原文、他人個人資料）。內部錯誤的詳細資訊只寫伺服器日誌，不得回傳客戶端。
- 訊息不得洩漏存在性：對無權存取的資源，錯誤訊息須與「不存在」不可區分（見 §6.3）。

## 3. 通用碼

通用碼適用全部前綴與全部端點。HTTP 狀態碼為標準語義，不得擅自改義。

| HTTP 狀態碼 | 錯誤碼（草案） | 語義 | 客戶端處理方向（見 §6） |
|---|---|---|---|
| 400 | `ETHER_VALIDATION_INVALID_REQUEST` | 請求格式錯誤（JSON 解析失敗、必填欄位缺失、型別錯誤等，無法定位單一欄位時用） | 不重試；修正請求後重送。 |
| 400／422 | `ETHER_VALIDATION_INVALID_FIELD` | 欄位驗證失敗（值域、長度、格式、業務規則不符，可定位欄位時用） | 不重試；依 `details` 修正欄位後重送。狀態碼用 400 或 422，定稿時二選一，全 API 一致，不得混用。 |
| 401 | `ETHER_AUTH_UNAUTHENTICATED` | 未認證（無 Token、Token 無效、Token 過期且無法刷新） | 嘗試刷新 Token（僅一次，見 §6.2）；刷新失敗則導向重新登入。 |
| 401 | `ETHER_AUTH_TOKEN_EXPIRED` | Access Token 過期（可區分於其他認證失敗時用，是否區分待定稿） | 同上，優先嘗試刷新。 |
| 403 | `ETHER_AUTH_FORBIDDEN` | 已認證但無權限（角色不足、非成員、非擁有者） | 不重試；不得以重試繞過權限。 |
| 403 | `ETHER_AUTH_BLOCKED` | 因封鎖關係被拒（草案；是否與「不存在」合併回傳待定稿，見 §6.3） | 不重試；不得向使用者揭露封鎖狀態。 |
| 404 | `ETHER_COMMON_NOT_FOUND` | 資源不存在，或呼叫者無權存取而以「不存在」回應 | 不重試；不得以 404 推斷資源是否存在。 |
| 405 | `ETHER_COMMON_METHOD_NOT_ALLOWED` | 方法不允許（路徑存在、方法不存在） | 不重試；修正方法。 |
| 409 | `ETHER_COMMON_CONFLICT` | 狀態衝突（重複建立、狀態機前置條件不符、版本衝突） | 不盲目重試；先讀取最新狀態再決定。 |
| 409 | `ETHER_COMMON_DUPLICATE` | 去重命中時的衝突表達（草案；訊息去重命中是否回傳已存在資源而非 409，待定稿，見 API_STANDARDS.md §7） | 依定稿行為處理；不得新建重複資源。 |
| 410 | `ETHER_COMMON_GONE` | 資源已刪除／已失效且不再可用（草案，是否使用待定稿） | 不重試。 |
| 413 | `ETHER_COMMON_PAYLOAD_TOO_LARGE` | 請求體／檔案過大 | 不重試；縮小後重送。 |
| 415 | `ETHER_COMMON_UNSUPPORTED_MEDIA_TYPE` | 不支援的內容類型／檔案格式 | 不重試；更換格式後重送。 |
| 429 | `ETHER_COMMON_RATE_LIMITED` | 限流（見 API_STANDARDS.md §9） | 按 `Retry-After` 等待後重試（見 §6.4）；不得立即重試。 |
| 500 | `ETHER_COMMON_INTERNAL_ERROR` | 伺服器內部錯誤（未分類） | 可重試一次（見 §6.4）；重試須帶同一冪等鍵，不得重複建立。 |
| 502 | `ETHER_COMMON_BAD_GATEWAY` | 閘道／上游錯誤（Traefik 後端不可用等，草案） | 可重試（見 §6.4）；重試間隔待定稿。 |
| 503 | `ETHER_COMMON_UNAVAILABLE` | 服務暫不可用（維護、依賴未就緒、降級） | 按 `Retry-After` 等待後重試；不得無限重試。 |
| 504 | `ETHER_COMMON_GATEWAY_TIMEOUT` | 閘道逾時（草案） | 可重試一次；須以冪等鍵保證不重複。 |

備註：

- 通用碼清單為草案，定稿時逐碼確認是否保留、合併或刪除；不得在未定稿前以本表為已定清單對外承諾。
- 驗證錯誤的狀態碼（400 或 422）定稿時二選一，全 API 一致；本文件不預寫二選一的結果。
- 伺服器錯誤（5xx）不得回傳內部細節；錯誤碼一律為通用內部錯誤碼，不得以資料庫、框架的原始錯誤碼回傳。

規則：

- 領域錯誤碼一律以 `ETHER_<領域>_<具體錯誤>` 形式命名，不得以通用碼表達領域專屬語義（例如群組成員上限不得以通用 `CONFLICT` 代替而不附領域碼，定稿時確認）。
- 具體錯誤碼（`<具體錯誤>` 段）須在各領域／各階段文件中逐碼定稿，含語義、HTTP 狀態碼、是否可重試、示例。本文件不預寫具體錯誤碼清單，不得以示例清單冒充定稿。
- 跨領域的同一語義（例如「資源不存在」）一律用通用碼，不得各領域自訂同義碼。
- 錯誤碼的增刪須經 API 審查，並同步更新 OpenAPI 文件與客戶端錯誤對照表，不得擅自增碼。

## 5. 錯誤回應格式

### 5.1 格式（草案，待定稿確認）

```json
{
  "error": {
    "code": "ETHER_VALIDATION_INVALID_FIELD",
    "message": "欄位驗證失敗。",
    "request_id": "01J...",
    "details": [
      {
        "field": "display_name",
        "issue": "TOO_LONG",
        "message": "顯示名稱過長。"
      }
    ]
  }
}
```

- 頂層鍵為 `error`（草案）；`error` 內須含 `code`、`message`、`request_id` 三項，不得省略 `request_id`。
- `request_id`：每次請求的唯一識別碼，由伺服器產生（格式待定稿，草案為不透明字串），貫穿請求日誌、錯誤追蹤（GlitchTip）與客戶端回報。客戶端回報問題時須附 `request_id`；伺服器日誌須以 `request_id` 可查。`request_id` 的產生方式（UUID 或其他）待定稿，不得以客戶端產生的識別碼代替伺服器 `request_id`。
- `details`：僅在欄位驗證失敗等可定位的錯誤時出現；每項含 `field`（欄位路徑，`snake_case` 點分隔，草案）、`issue`（機器可讀的問題碼，值域待定稿）、`message`（人類可讀說明）。`details` 不得含敏感資訊，不得含未授權的欄位資訊。
- 不得在錯誤回應中附加成功回應的資料欄位；錯誤回應與成功回應的頂層結構不得混用。
- 錯誤回應的 `Content-Type` 為 `application/json`；HTTP 狀態碼須與錯誤語義一致（見 §3）。

### 5.2 閘道層錯誤

- Traefik 產生的閘道錯誤（例如後端不可用、逾時）須盡量轉譯為本文件格式（含 `request_id`），轉譯方式待部署文件定稿；無法轉譯時，客戶端須以 HTTP 狀態碼判讀，不得假設閘道錯誤必含本文件格式。
- 閘道錯誤的 `request_id` 須與後端日誌可關聯（關聯方式待定稿），不得以兩套識別碼無法關聯而不說明。

### 5.3 WebSocket 錯誤

- WebSocket 事件層的錯誤（認證失敗、事件格式錯誤、限流、序號錯誤等）以 WEBSOCKET_PROTOCOL.md 的錯誤事件／ACK 格式為準，不得以本文件的 HTTP 錯誤回應格式直接套用於 WebSocket。HTTP 錯誤碼與 WebSocket 錯誤碼的對應關係，待 WEBSOCKET_PROTOCOL.md 定稿時明定，不得以本文件假裝已對應。

## 6. 客戶端處理原則

### 6.1 一般原則

- 客戶端一律以錯誤碼（`code`）判讀，不得以 HTTP 狀態碼文字、訊息文字（`message`）、訊息語言判讀。
- 未知錯誤碼須按「通用伺服器錯誤」處理（顯示通用提示、記錄 `request_id`），不得崩潰、不得靜默忽略、不得以舊版對照表誤判。
- 錯誤發生時，客戶端須保留使用者已輸入的內容，不得清空輸入框、不得遺失草稿（草稿保存規則見各功能文件）。
- 所有錯誤狀態須有對應的 UI 狀態（Loading／Empty／Error），不得以空白畫面、無反應代替錯誤提示。

### 6.2 認證錯誤處理

- 收到 401 時，客戶端先嘗試以 Refresh Token 刷新 Access Token，僅嘗試一次；刷新成功後，以原請求（同一冪等鍵）重送一次；刷新失敗或再次 401 時，導向重新登入，不得無限重試刷新。
- 收到 403 時，不得重試、不得以切換帳號以外的手段繞過；須顯示無權限提示，不得揭露他人資料或封鎖狀態。

### 6.3 存在性與封鎖

- 收到 404 時，不得向使用者斷言資源「不存在」或「已被刪除」，僅顯示通用提示；不得以 404 的有無推斷封鎖關係、帳號存在性。
- 封鎖相關的拒絕，伺服器端須回傳與「不存在」不可區分的錯誤（錯誤碼與訊息皆不可區分，具體方式待定稿）；客戶端不得以錯誤差異推斷封鎖狀態，不得向使用者顯示「你已被封鎖」。

### 6.4 重試原則

- 可重試的錯誤：限流（429，按 `Retry-After`）、服務暫不可用（503，按 `Retry-After`）、伺服器內部錯誤（500，僅一次）、閘道錯誤（502／504，僅一次）。重試次數上限、退避間隔，一律待定稿，不得預寫數字；重試須採退避（Exponential Backoff 方向），不得立即連續重試。
- 不可重試的錯誤：驗證錯誤（400／422）、認證／授權錯誤（401／403，已按 §6.2 處理者除外）、不存在（404）、狀態衝突（409，須先讀取最新狀態）、請求過大／格式不支援（413／415）。
- 重試寫入請求時，須帶同一冪等鍵／`client_message_id`，不得產生重複資源；重試讀取請求時，不得假設重試結果與首次一致，須以最新回應為準。
- 離線／弱網下的重試，見 WEBSOCKET_PROTOCOL.md（ACK／重試／去重）與離線佇列文件；HTTP 重試與 WebSocket 重試不得互相代替。

### 6.5 錯誤回報

- 客戶端回報錯誤時，須附 `request_id`、錯誤碼、發生時間、App 版本、平台，不得附密碼、Token、訊息明文、E2EE 內容。
- 錯誤追蹤以後端 GlitchTip 為準（自架，見部署文件）；客戶端不得將錯誤詳情上傳至未經批准的第三方錯誤追蹤服務。

## 7. 版本與廢棄

- 錯誤碼的增刪改須隨 API 版本管理：新增錯誤碼為向後相容變更（客戶端須能處理未知碼，見 §6.1）；刪除／改義錯誤碼為破壞性變更，須升級主版本或經廢棄期（廢棄期長短待決定，不得預寫）。
- 廢棄的錯誤碼須在 OpenAPI 文件中標示廢棄，並保留至廢棄期屆滿；廢棄期內伺服器不得以新碼代替舊碼而不通知客戶端開發者。
- 每次錯誤碼變更須同步更新：OpenAPI 文件、客戶端錯誤對照表、測試案例（錯誤碼測試見 TEST_STRATEGY.md），不得只改伺服器而不改文件。

## 8. 缺口與待定稿事項

1. 錯誤回應包裝（頂層鍵、`details` 結構）為草案，待定稿確認，並與 API_STANDARDS.md 的成功回應包裝規則一致定稿。
2. 驗證錯誤的 HTTP 狀態碼（400 或 422）待二選一，全 API 一致。
3. 封鎖拒絕與「不存在」的不可區分方式待定稿（含錯誤碼是否合併）。
4. 訊息去重命中的回應行為（回傳已存在資源或 409）待定稿。
5. 具體領域錯誤碼清單未定，須在各階段逐碼定稿，本文件不預寫。
6. 重試次數、退避間隔、`Retry-After` 格式、限流數值，一律待定稿／待查證。
7. `request_id` 格式、閘道與後端 `request_id` 的關聯方式，待部署／日誌文件定稿。
8. WebSocket 錯誤碼與 HTTP 錯誤碼的對應，待 WEBSOCKET_PROTOCOL.md 定稿。
9. 舊規格的錯誤表達（如 Supabase 錯誤、舊端點的錯誤回傳）與本規範的差異，須寫入 ADR，不得以舊表達實作。
